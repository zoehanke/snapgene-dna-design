## 1. 核心判断

Evidence Trace 应优先证明：**哪些要求和材料被提交、程序实际执行了什么、哪些结果影响了后续输入、交付文件对应哪次执行；再附上有来源的设计说明。**

同期解释有价值，但不是可信度基础。它最多先证明“当时说了这句话”，不能单独证明“这句话就是导致选择的真实原因”。同样，程序记录某个参数，不意味着 AI 自主选择了它；存在论文，不意味着模型当时读过；后来验证成功，不意味着原决定已有充分依据。

目标应是让读者能发现不一致、缺失和越界推断，而不是让每个决定都看起来理由充分。记录稀疏但来源明确，优于内容丰富却无法核对的故事。

检索重点为 2026 年 6 月至 9 月；较早基础工作单列。预印本、方法演示与已部署工具不按同一证据强度处理。以下是对本项目有实际设计价值的部分，不是领域穷尽清单。

这些资料支持的是方法选择，不足以声称“忠实解释已经解决”。本文的架构组合是针对仓库约束作出的工程建议。

| 候选路线 | 可信度收益 | 成本/干扰/复杂度 | 判断 |
|---|---|---|---|
| 每项选择都强制同期解释 | 减少遗忘，保留公开承诺；不自动得到真实因果 | 额外 token、可能改变选择过程、容易为填字段编理由 | 保留在 Full 的少量关键选择，不作唯一依据 |
| 完成后让另一个模型整理完整证据链 | 可读性可能改善，但会引入新的推断与补叙 | 多一次或多次调用，还需检验生成的关联 | 不作默认事实生成器；明确标识的辅助解释可保留 |
| 重建 agent harness，强制代理全部工具 | 可观察面更广，且有更强采集控制 | 改变现有 Skill 使用方式，宿主适配与维护成本高 | 当前不选 |
| 现有 wrapper + 窄宿主来源适配 + 确定性投影 | 在可见范围内保留可核查事实，清楚区分声明和结果 | 基础日志无额外解释调用；增加有限本地 I/O 和适配维护 | 推荐主架构 |
| 每次选择都做反事实重跑 | 检查特定输入是否影响行为 | 需要大量额外采样；不是原运行的内部因果证明 | 只作离线抽查，不进入正常 DNA 主线 |

## 3. 仓库已经具备什么，实际缺什么

| 现有实现 | 可直接保留 | 可信度缺口 |
|---|---|---|
| `runtime.py:observe()` | 调用前输入、调用返回/异常、`stage_ref` | 主要覆盖接入的入口和阶段，不等于宿主所有检索、讨论、原子操作都被观察；汇总返回不能包装成逐项独立观测 |
| `TraceRun.capture()`、`capture_files()` | 真实结果生成 Validation/Artifact；现有内容锚点与返回事件引用 | `same_run` 是运行级关联，不能表示某项检查证明了所有 Decision/Claim；文件引用也不自动证明某段材料已并入产物 |
| `recorder.py` | 追加事件、节点修订、已有引用、独立后补说明、冻结运行上下文 | 记录时间不等于原事件发生时间；JSONL 的追加约定和哈希不能抵抗同权限写入者主动改造历史 |
| `provenance.py` | 分开提交者、选择者、原说明和后补说明 | `decision_source.reference` 目前主要检查非空，未核对宿主原事件。`ai_concurrent` 是来源声明，不是程序已证明的同期性 |
| `coverage.py` | 识别已知字段并匹配 Decision 目标值和范围 | 不知道未接入工具与未识别字段；匹配成功只证明声明与参数相符，不能证明理由因果有效 |
| `reader.py` | 统一过程、条件旁支、确切版本、材料关联歧义、运行筛选 | 必须继承来源强度，不把来源声明在文案中升级为已核实事实；现 HTML 尚未消费新投影 |

本轮执行了一个不写文件的最小探针：给 Decision 填入无宿主凭据的 `reference="unverified-placeholder"`、`ai_concurrent` 和非空理由，现有函数接受，投影返回“AI 当时说明”、`original_explanation_recorded=True`。这证明当前标签依赖声明，不代表已经发现某次真实设计被伪造。

因此主要需要补的是**来源校验、发生阶段和采用关系**，不是再建图数据库、独立科学验证引擎或重写 DNA Core。

## 4. 建议架构：一份事件日志，两类记录，统一阅读投影

```text
宿主可提供的公开原事件 ──────┐
                            ├→ 现有 Recorder → events.jsonl
现有执行 wrapper 的实际观察 ─┤                       ↓
用户/模型提交的说明与证据 ───┘             关联与来源检查 → reader → HTML

DNA 主线继续使用原有入口、参数、planner、Handler、Validation 和正式产物。
```

### 4.1 先分清观测事实与提交声明

事实包括“wrapper 在该调用收到参数 X”“原工具返回结果 Y”“文件 Z 对应该次生成”。声明包括“用户想要 X”“AI 因为 Y 选择 X”“文献支持当前判断”。

声明仍是重要记录。核实原消息可以证明是谁说过什么，但内容是否科学成立还需另查。运行程序的检查结果也只能代表该程序、该版本、该检查范围。

不新增第二份事实库。复用 `stage_ref`、`result_event_ref`、`basis_refs`、运行与版本引用。来源元数据只补当前无法表达的三件事：采集通道、可核对的原事件位置、原事件时间/顺序。具体字段形状在实现前用现有事件确定，不先铺一套泛化 schema。

由 collector 填写采集通道及核对结果。宿主/模型自由提交的 JSON 不能自行赋予“已由 collector 核实”的身份。这是应用内部约束，不宣称构成对恶意同权限代码的安全隔离。

### 4.2 两个采集范围，同一产品

**基础范围：Skill 边界。** 默认安装即可记录真实输入、调用、结果、失败、产物；能证明某份说明在调用前已经提交，不能因此证明它来自同一次模型响应。绕过 wrapper、未接入的原子工具和宿主外部行为仍是未观察范围。

**增强范围：宿主原事件。** 有可用的公开事件接口、hooks 或用户导出的原记录时，窄适配器核对相关用户原话、公开模型说明、工具调用和返回。优先试点用户实际使用的一个宿主；本轮尚未验证其稳定接口，不能承诺任意宿主通用。

适配只读取明确指定的任务事件，不默认收集完整对话、其他任务、隐藏推理、凭据或全量序列。它将必要片段及原引用交给同一个 Recorder 串行追加，不让多个 hooks 并发改写单写入者日志。不把读取客户端私有数据库作为长期产品契约。

适配器未安装或事件缺失时，基础功能仍可用，显示真实采集范围。不得用模型转述补成已核实的宿主记录。全局 off/observed/full 决定采集内容，不代表已经取得某种宿主可见性。

### 4.3 采用关系从实际参数建立，不由叙述决定

保留选择提案与实际执行的区别。一个 Decision 可以存在但未采用；执行可以存在但原决定未记录。

将已有 `targets` 匹配定位到具体调用和输入版本。选择 X、实际调用 Y 时，保留两者并显示不一致，不自动改 Decision 或替用户解释原因。失败与重试各有原事件；并行分支保持并行。

对内部步骤只利用现有返回中可定位的执行结果。没有逐步凭据时明确为汇总记录，禁止为展示完整而编出逐步事件。检查细分仅投影 Core 已经给出的真实内容；不新增验证语义。

### 4.4 证据的“支持”和“当时可用”必须分开

继续使用 Source → Statement → Claim → Decision，不把一篇论文整体挂成正确性证明。优先保留相关原片段、页/节/表定位、版本及所见范围，链接回已有检索/工具返回；只看到摘要就不写“核对了全文”。

分别回答：来源是否被核对过；具体片段说了什么；何时被观察或提交；提交者声称支持哪个方面；当前条件适用到哪里。若宿主日志仅显示工具返回，不足以证明模型实际读懂或使用了该内容。

证据内容、理由和限制可能来自不同时间，不要让 Decision 上一个“同期”标签替整个旁支背书。后来来源可以支持早先选择的合理性，但不进入其“当时依据”视图。已有迟到导入若携带更早原事件，则分别保留原事件时间和本次采集时间；不能一概判为后写解释。

时间比较优先使用同一事件流的顺序及调用关系。跨进程时间戳不足以单独证明先后；缺少可比较锚点时记为无法核实。

### 4.5 用少量明确检查发现故事与事实不符

扩展现有 provenance/coverage/projection，限于实际可判定的问题：

- 声称同期的说明没有对应原事件，或原事件明确晚于执行。
- 声明的选择与该调用实际参数不符；关联目标含糊时保持未知。
- “当时依据”引用了当时尚未出现的来源；后补支持不自动算历史错误。
- 引用的程序结果属于另一次运行、旧产物或不同检查范围。
- 接入边界内有调用开始但无返回，或真实失败/重试在默认阅读中被漏掉。

这些检查只标记录矛盾与待核对处。来源在句义上是否足以支撑复杂生物学外推，仍由研究者判断；暂不接自动评分、持续模型裁判、自动重算或 DNA 准入控制。

## 5. Full 如何保留价值而控制成本

继续保留一套 Skill、全局 Off/Observed/Full。开发默认 Full 保持现有决定；发布默认尚未冻结，需要实际成本比较。

Observed 提供同一条事实骨架，保留已有用户理由和模型已提交说明，不强求额外生成。Full 只在有真实取舍且影响构建结果时，随原设计响应附带一句选择说明、已有依据引用和当时已识别的重要限制。

优先记录来源/元件、边界与方向、stop policy、方法、突变组合和候选取舍；用户已明确规定的值引用其要求，不再逐参数重述。理由、依据、限制可同次提交，但不强制填满三栏，也不虚构未考虑过的替代方案。

尽量通过现有 `trace_input` 随执行提交，复用短引用，不复制论文段落进多轮提示，不增加解释专用模型调用或一个专门审查的 agent。已有 `record` 入口保留给独立发生的真实决定，不强制每个调用前后都增加记录轮次。

标签建议表达为“已核对原消息”“调用前提交的说明”“来源由提交者声明”“后来补充”。具体短文案需在现有阅读框架内验证，不新增一屏可信度等级。

必须区分两项实验：固定 DNA 输入的 Trace 三档对照应该等价；真实宿主改用 Full 后，额外说明可能改变模型行为。前者不能证明后者无干扰。需要测整次任务的新增输入/输出 token、工具轮次、耗时和任务成功情况，而不是只数 rationale 字数。

## 6. Reader Demo 与 HTML 怎样体现可信度

保留已通过负责人静态审阅的 GFP 三组比较故事。当前草稿是模拟对话和历史结果回放，它验证阅读组织，不证明那些 AI 说明曾在历史执行时发生。

正式演示从同类自然请求重新运行，记录当次真实选择、来源和结果。不要求模型复述旧脚本，不人为要求它犯错或安排用户否决。确有修改、失败、补录时保留；没有就不添加。GFP +3 bp 继续只做工程回归。

默认 HTML 仍然是背景 → 要求/选择/程序结果/产物，理由和证据为旁支。普通读者需要看到实际动作、原说明来源及会影响理解的冲突；不需要看到每项来源检查字段。

例如：模型声称使用某中间体，程序实际输入却是另一个文件。主链应直接显示实际来源和不一致，旁支保留原说明。不能用一段更圆滑的解释让主链看起来一致。

Document、Mind Map、Split 继续共用 reader。普通顺序不画成科学因果；“当时记录”与“后来补充”能区分；关键失败不能被折叠隐藏。Review 只列具体可处理问题，不把 Observed 缺额外说明或一般性文献局限全部变成红灯。

## 7. 建议实施计划

在当前 Phase 3.1 第四步与第五步之间补一个有界的“来源与关联收口”，然后继续原 HTML 工作。不重启 Phase 1 至 3，不提前进入 Phase 4。

| 顺序 | 最小修改范围 | 可交付结果和通过条件 |
|---|---|---|
| 1. 确认可信度契约 | 接受方案后修订 safety spec、core spec 的相关边界、design.md 标签、Phase 3.1 与索引 | “声明”和“已核对来源”分开；输入/执行/验证区别明确；现有静态审阅不被重置。没有接受的产品决策保持候选 |
| 2. 收口基础记录 | `provenance.py`、`runtime.py`、`recorder.py`、`coverage.py` 及必要 CLI/说明 | 同期性不靠自填字段升级；原说明与确切调用输入关联；晚补、失败、重试和历史版本可检查。普通 Trace 故障继续不改变 DNA 主线 |
| 3. 一个宿主来源试点 | 一个窄适配入口，相关测试/用法；不建通用宿主框架 | 用真实可用接口核对一次用户原话、公开选择说明与调用关联。接口不支持的部分明确记录为不可核实；不以脆弱私有数据库适配冒充支持 |
| 4. 接回原步骤 5/6 | `reader.py`、renderer/view、映射、可执行 Reader Demo 和相关测试 | 来源区别进入可读页面；程序实际产物与记录逐项对应；三视图、人类理解、三档回归完成后再交付 |

第二项不能扩张为通用科学推理引擎，第三项不能成为所有用户必须安装的服务。若宿主试点无法稳定提供原事件，就交付诚实的 Skill 边界版本，明确不声称已经完成宿主级来源核实。

### 验收围绕三类真实流程，不扩建大型 benchmark

1. 简单构建：无额外 Decision 也可完整阅读实际要求、检查与产物。
2. 三组比较：源材料及中间体去向可查，论文对候选的支持不冒充对路线或性能的证明。
3. 修改/重试流程：使用真实改动或原失败案例，旧检查、实际参数及后补说明不混用。

在这些流程上加入针对性反例：伪来源引用、晚到说明、错参数关联、旧 PASS 配新产物、丢失调用返回。分别统计应发现的矛盾、误报及无法判断项；正常稀疏记录不应被误判为错误。人工注入反例标为测试，不伪称真实模型事故。

固定相同输入通过三条公共入口做三档 DNA/注释/引物/制备/验证语义/正式文件对照，复用已有测试。对少量真实宿主任务再做 Off/Observed/Full 成本试验，记录实际额外轮次和总 token；有随机波动就重复并报告范围，不用一次运行宣称平均性能提升。

反事实验证只作为离线研究抽查：例如变更一条被声称关键的约束，观察路线分布是否随之改变。控制其他条件并重复采样；变化说明敏感性，不等于恢复了原模型内部因果，没有变化也不直接证明理由虚假。首版不实现自动 CHIVE 流水线。

真人页面审阅除原理解题，再检查：能否分清实际做了什么与谁声称为什么；能否区分当时依据和后来支持；能否找到一项具体检查的范围及对应文件。答不出就修改表达，不能以日志完整率替代验收。

## 8. 前序事项与长期维护

| 既有事项 | 本方案处置 |
|---|---|
| Phase 3.1 第四步 reader 已完成，第五步 HTML 未完成 | 保留投影和通过记录；补来源语义后继续第五步，避免对错误标签做精美包装 |
| 静态稿已获负责人接受，但双人计时未实施 | 保留接受事实；不补写计时，最终页面另验。草稿局部旧状态文字以后按实际版本整理，不覆盖用户编辑 |
| 原始程序结果、旁路不干预、单一事件源、既有哈希 | 全部保留；不新增哈希链、签名、区块链或第二套存储 |
| 入口/字段覆盖有限、单写入者、来源声明、产物路径 | 本轮收口来源声明与调用关联；其余明确保留。仅有 digest 而无原材料时不能承诺可重跑 |
| Source verification、Applicability、Change Impact | 保留当前独立语义，不做额外科学判断；后补核查不改原记录 |
| Full 总成本、发布默认、人类理解 | 进入实际小样本比较，未测量前不宣称低开销或效率收益 |
| Assurance Case、Conclusion Boundary、宏观框架 | 继续延期，不借可信度改造扩大为安全治理系统 |

长期最值得防止的不是少几个字段，而是记录在重建、摘要、晚补、换版本后逐渐被说得更确定。原始事件只追加；新增核查追加结果；旧缺失保留未知；投影算法版本可识别；读取旧运行时不混入未来知识。

本轮推荐的可信度范围是防止遗漏、混淆和不实补叙，并使错误可发现。若未来要求抵御宿主主动篡改其可写文件，需要独立写入权限或外部信任锚点，那是另一项经过明确授权的产品决策。当前不以“追加式日志”宣传防篡改认证。
