# 项目演进与关键决策

## 用途与维护规则

本文帮助新开发者或 AI 理解：项目为何形成当前目标、架构和规范，以及哪些反馈改变了方向。**Spec 写“现在应该怎样”；History 写“为什么变成这样”**。具体代码看 Git，测试与阶段交付看[开发计划](development-plans/README.md)，问题细节看原审计；本文不复制这些流水记录。

- 只记录影响产品方向、模块边界、接口/Schema、工作流或长期开发规则的变化。普通修复、日常讨论和测试数量不逐项收录。
- 以追加为主。决定被推翻时新增记录并指向旧决定；纠正历史事实时注明更正及来源，不抹去当时判断。
- 重要反馈写清提出者/来源、当时背景、问题、采纳状态和最终调整；未采纳或延期需写原因。来源不明就注明，不补造 Reviewer、指导者意见或准确日期。
- 区分提出、采纳、实现、验证。计划写过、原型展示过、CI 通过过，都不等于正式功能或科学结论已成立。
- 涉及长期边界或开发规则时，同次更新对应 Spec。历史意见不自动成为当前任务或永久禁令；当前有效要求以 Spec 和用户明确任务为准。
- 开发者、Reviewer、指导者或用户的意见一旦实际影响方向，应在交接前整理进本文，不能只留在聊天中。无需为未影响方向的每条意见建档。

本次于 2026-09-20 根据仓库材料与项目负责人在本任务中的讨论首次归纳。以下日期表示可核对的阶段，不为无时间戳的讨论补造精确日期。当前规范入口：[主 Skill](../specs/core-skill.md)、[Evidence Trace](../specs/safety-module.md)、[阅读设计](development-plans/design.md)。

## 1. 早期审查：先修真实构建通路，收缩元框架

**来源与背景**：2026-09-05 至 09-06 的[首轮审计](IGEM-2026-SOFTWARE-AND-SAFETY-AUDIT.md)发现，已有大量工具和通过的测试，仍存在酶切、复合特征、注释传递及空验证凭据放行问题。部分目标验证只证明“产物符合计划”，没有证明“计划符合用户要求”。

**关键反馈**：项目负责人否定了为这些修复再建独立 `goal_validation.py`、多层验收矩阵和大型 Benchmark 的做法，要求优先让真实质粒正确交付。后续又明确：主干尚未可靠时，不应优先扩建 Construct Review。

**处理：采纳并收缩范围。** 在现有验证入口检查 required/forbidden components；采用 Biopython 原生特征提取；修复实际反应和注释链，拒绝空凭据。Construct Review 暂缓，不代表永久否定审查功能。拒绝的是当时缺乏收益的重构规模，不是禁止以后为真实复杂度增加模块。[修订后的计划](IGEM-2026-DEVELOPMENT-PLAN.md)

## 2. 真实任务与复查：文件生成不等于完成生物设计

**来源与背景**：2026-09-06 至 09-08，项目负责人要求用论文材料和独立执行任务检验 Skill，而非继续累积抽象测试。[真实任务复查](REAL-WORKFLOW-REPAIR-20260907.md)暴露出模板来源、实际 PCR、中间体传递、表达边界、骨架制备和 guide 结构等问题。

**关键反馈**：不能用预设目标片段代替从真实模板和实际引物推导的扩增产物；不能改变测试的生物学目标、删掉有问题的注释或伪造检查指标来获得绿灯。

**处理：采纳并确立主线原则。** 组装消费真实制备产物，交付绑定落地文件与原检查；保留骨架、插入片段和引物注释。后续[完整性复查](INTEGRITY-AUDIT-AND-REPAIR-20260907.md)发现早期修复中仍有错误判据及被改动的 GOI，撤销目标改动并重做通路。无法实施复杂编辑的关键词入口明确拒绝，转向 Recipe/ConstructionTask；部分审查误报也经实际序列、环状旋转和输入契约核对后撤销，没有扩张为新规则。

2026-09-08 的 [v1.0.0](RELEASE-v1.0.0.md)记录了当时已验证的可用范围。它不是“所有后续真实材料均无缺陷”的承诺。产品优先服务一般分子与合成生物学研发，iGEM 展示价值建立在真实效用之上。

## 3. 安全方向探索：从附加审查转向设计过程的可复核性

**来源与背景**：2026-09-08 至 09-10，项目负责人希望安全模块依附现有 Skill，同时增强软件价值，并保留 iGEM 生物安全方向的竞争可能。仅提醒研究者粗心，被认为不足以回应 AI 参与研究的不确定性；独立生造宏观治理体系又不适合短周期。

**关键反馈与处置**：采纳“从项目需求出发、融入主体工具”的方向。Genome Resurrection 提供了讨论 DNA 存在、功能恢复与生态后果之间差距的背景，但软件不因此宣称可判断物种复活或生态安全。早期[范围保真/权限控制方案](AI-BIO-SAFETY-30DAY-ROUTE-20260909.md)曾被推荐为候选，最终未成为当前主线；受控宿主与运行器隔离尚未闭环，不能写成已实现的安全系统。

最终选择先做 Evidence Trace：留下要求、选择、依据、程序结果和产物的可审查记录。风险评分、safe/unsafe、生态预测和完整安全论证暂缓；奖项竞争力是目标，不是已有验证结论。

## 4. Trace 第一阶段：旁路记录，保留证据的条件与边界

**来源与背景**：[Phase 1](development-plans/safety-phase-1-trace-v0.1.md)承接项目负责人的明确约束：主核心负责设计，Trace 负责记录与解释过程，不反过来改变 DNA、执行参数或验证语义。

**处理：采纳。** 采用追加式 `events.jsonl` 作为事实源，复用任务、执行和文件的现有版本锚点；图与报告可重建。记录关键生物学选择，普通文件操作不强行塞进科研叙事。正常模式下 Trace 故障不拖死 DNA 工作，严格停止作为独立显式策略。

证据结构选择 `Source → Statement → Claim → Decision`，而非“一篇论文直接证明一个决定”。支持、反对、限制、条件及适用范围分别保留；来源存在、证据适用和结论正确不是同一件事。Validation 与 Artifact 只能来自真实程序结果，模型不能自行填写通过凭据。

## 5. Phase 2/3：观察实际选择，并标出变化的影响

**来源与背景**：记录依赖 AI 主动提交，且证据数量增加后页面难读。[Phase 2](development-plans/safety-phase-2-applicability-v0.2.md)引入实际输入选择的覆盖检查与证据条件比较；[Phase 3](development-plans/safety-phase-3-change-impact-v0.3.md)增加 Change Impact。

**关键反馈：采纳但限制推断。** 漏记显示为未解释的实际选择，不事后补造 rationale；条件匹配不等于科学适用。变化是带前后版本的正式记录，影响判断保守：未找到依赖不等于无关。重评、重查、重跑建议与原验证结论分开，不自动执行反应或把旧结论改为错误。

当时采用以 Decision 为中心的局部图，并保留高级网络视图。这缓解了复杂度，但后来真人阅读反馈表明，局部关系完整仍不足以让陌生读者理解整个任务，因此默认组织方式再次调整。

## 6. 可读性反馈：从节点展示转向完整设计过程

**来源与背景**：项目负责人多次指出，页面虽然有很多信息，却没有先说明项目目标、用户要求和设计如何形成；默认暴露 Claim、revision 等内部概念，也让科研阅读变成系统审计。

**处理：采纳。** Evidence Trace 保留为记录系统名称，Design Decision Trace 是默认人类阅读方式。主线改为完整任务，理由、证据和限制归属具体步骤；栏目按真实内容出现，普通任务不强制制造论文链、用户否决或待实验问题。[补救计划](development-plans/safety-phase-3-readability-v0.3.1.md)

GFP 末端 +3 bp 被认为缺乏完整研究语境，保留为工程回归；另建三组同背景 GFP 比较的 [Reader Demo](development-plans/safety-phase-3-reading-draft.md)。案例认可、静态理解、浏览器检查和最终真人试读分别记录，不相互代替。

后续原型反馈进一步改变视觉规范：保留紧凑导航、章节表面和语义颜色，同时减少框架内部噪声；结果摘要前置，图文选中状态明确对应。项目负责人提供了[视觉参考图及设计稿](development-plans/evidence-trace-report-visual-design-v0.3.1.md)。另明确否定手写“AI 的三项公开选择”这类案例栏目：真实选择可能有不同数量，报告必须来自数据，不能靠漂亮原型掩盖组织缺陷。

## 7. 可信度复审：同期解释不是整条链的可信基础

**来源与背景**：2026-09-14 至 09-15，项目负责人要求重新考虑闭源、调用工具的宿主模型如何被记录。[可信度研究](EVIDENCE-TRACE-TRUST-ARCHITECTURE-20260914.md)和[真实使用审查](EVIDENCE-TRACE-REAL-USE-AUDIT-20260915.md)显示，声明了同期理由不等于核实了其发生时间或内部动机。

**实际暴露**：日志可以显示完整，却漏掉最终四份引物标注文件；宿主检索和原始说明部分只有描述性引用；用户约束也曾被包装成 AI 自主决定。候选序列与目标相符，不消除源载体注释导致的正式交付阻塞。

**处理：采纳证据获取优先的修正。** 优先捕获实际输入输出、原资料、来源定位及文件处理；分清提交者、选择者、原说明与后补解释。保留少量同期公开理由，但不把它当作可信度唯一基础。通用宿主接管、额外遥测服务、哈希链/签名工程和逐决定反事实重跑均未选为默认路径；它们不能直接解决本项目已经证实的采集缺口。

## 8. 三层方案 r2 及实现：数据层交出已组织的完整过程

**来源与背景**：2026-09-19 至 09-20，项目负责人追问：程序虽能连接明确引用，谁来理解阶段、取舍、依据和整体设计思路？此前“纯程序投影已经能整理完整过程”的设定因此被修正。[Archify 对照](ARCHIFY-REFERENCE-REVIEW-20260919.md)提供了“作者组织结构化内容、固定程序生成视图”的参考，但其图形 Schema 和校验不构成科学真实性保证。

**处理：采纳并实现。** [三层方案](development-plans/safety-phase-3-three-layer-design-v0.3.1.md)明确：采集层留原记录；数据层由宿主 AI/人做语义组织，程序核对事实引用与版本；报告层按保存的编排固定生成 HTML/Markdown。`graph.json` 包含完整过程，`report_plan` 单独表达阅读顺序、摘要和折叠取舍。AI 可同次提交两者，但仍有真实 token 和时间成本。

原日志仍是事实源，组织与编排版本也追加其中；新事实使旧组织陈旧，缺组织时显示有限事实。未采纳独立模型服务、图数据库或另一套长期 `report.json`，也未直接搬入 Archify 编译器。报告不再首次创造科学关系，不再在每次导出时调用模型。

为兼顾成本与记录需求，保持一套 Skill 的 Off/Observed/Full：不采集、观察事实、观察事实并由宿主补关键公开说明及过程组织。没有拆成安全版/普通版，也没有引入会话状态系统；Observed 中已有的真实用户理由仍保留，Full 不保证模型内部解释真实。

实现覆盖三个设计入口及检查、引物标注、转换、预览导出；实际两组 GFP 任务中，四份末端 QC 文件已能追到标注动作。门限失败前已经写出的候选也被记录。正式页面使用实际组织数据，未沿用示例中的固定数量与成功结论。具体实施与跨平台证据保存在[阶段交接](development-plans/safety-phase-3-readability-v0.3.1.md)，不在此复制测试清单。

## 9. 规范治理：允许基于证据修订旧规则

**来源与背景**：2026-09-20，项目负责人明确授权：原 spec 或计划阻碍正确、实用的开发时，应优化修改，而非机械执行或反复请求已经给过的权限；同时要求建立本历史文档。

**处理：采纳。** 当前规范保留有效目标、边界和接口契约，把旧阶段顺序、实现建议与历史验收要求分开。例：静态试读仍用于重要阅读组织变更，但“所有 HTML 修改都先等待新一轮试读”的笼统限制被替换；已获授权的修复可推进，不能据此伪称真人验收通过。

未来变更在当前任务授权内说明原因、更新受影响 Spec/计划，并把重大转向及参与者反馈追加到 History。允许重构不意味着允许改目标求通过、伪造证据、降低验证门槛，或擅自修改 main。

## 10. 真实使用反馈：主任务优先，报告详情仍必须给人读

**来源与背景**：2026-09-20，项目负责人提供《第一次测试skill.docx》及 DSH、Trae、Codex 的 CDC15 测试产物。此前工程验收后，仍出现主结论被注意事项覆盖、首次漏交付 Trace 链接、生成文件 untraced、默认展开满是机器字段等问题。用户认可的是清楚的主方案网页和替换示意图，并明确指出“全面信息归数据层，报告层包括点开后的内容都应面向人”。

**实际核对**：DSH 日志三次记录引物绑定区间不匹配；两个大 HTML 约 96 MB、20 MB，存在大对象重复展开；三个交付清单分别有 10、2、1 个 untraced。没有据此确认模型所述的坐标根因，也没有把体积全部归因于完整 DNA 未省略。不同宿主和输入背景不能直接用于模型排名或提示词因果判断。

**处理：采纳为下一轮修复契约，尚未完成实施。** [实用性计划](development-plans/workflow-phase-3-usability-repair-v0.3.2.md)先修主任务判断与文件正确性，再补采集、去重及报告。主 Skill 增补复用优先和首次交付要求；设计阶段与 Trace 组织阶段的提示负担将通过受控对照调整，未直接切换默认模式。默认详情改为选择、文件、证据、检查各自的可读内容，原始字段移入独立技术入口；untraced 属于记录缺口，不自动成为科研待办。

此次转向保留三层分工，但否定“程序不改 DNA 就已经没有设计干扰”和“把 JSON 藏进侧栏就算可读”的做法。既有生物学验证不能因追求回答直接而删掉；新的可用性结论必须由原案例、实际文件和人类理解支持，不能再次只由 CI 通过推导。


## 11. 实用性修复：实际坐标优先，阅读详情与机器存储分开

**来源与背景**：承接第 10 节的测试反馈，本轮从原 DSH 参数复现故障。PCR 已迁移特征位置，但旧引物坐标仍覆盖当前位置；部分被截断的引物也被当作完整结合位点导出。

**处理：采用根因修复。** 导出使用当前特征位置并核验原结合序列；残片保留成明确的部分注释。拒绝删注释或放宽错配检查。三档真实产物一致，原完整参数不再因这项导出错误中断。

报告过去把原始对象藏进抽屉，仍要求研究者理解机器字段。本次按文件、选择、来源和检查产生可读详情；完整原数据留在独立技术文件。重复的运行/审计内容改用引用，HTML 不再内嵌整份机器图。选择此方式是为保留完整证据与离线阅读，未新增压缩服务、模型服务或另一个事实源。

**采纳但未验证的部分**：设计指导与完整 Trace 组织提示分阶段加载，保留 Full 默认。尚未完成受控宿主对照，因此不能归因或声称提示干扰已消失。原 pET/Chr1 注释与表达边界也未被豁免：真实检查仍保留。工程测试、真人理解、模型行为、实验效果继续分别说明。具体证据及下一步见[本轮计划](development-plans/workflow-phase-3-usability-repair-v0.3.2.md)。


## 12. 示例回归不足以支持完成判断

**来源与背景**：2026-09-21，项目负责人要求复查是否“示例产物正确就认为开发完成”，甚至按特定答案开发。

**结论与采纳**：未找到 CDC15 答案特判，但独立反例证明前轮验收偏窄：坐标排序会掩盖乱序源注释；完整碱基数掩盖线性切断的结合位点；报告漏掉未列入白名单的真实失败，并串联不同主体的证据；变化内容还被撤成技术文件入口。此前宣称工程完成的范围据此收缩，旧测试记录保留，不把过去改写成已覆盖。

修复依据是原生物学顺序、物理连续性、证据归属与人类报告应保留的实质内容，而非示例答案。验收增加独立有效/无效输入与相互矛盾的记录；详细数据不能依赖是否进入正文才可读。当前 Spec/AGENTS 同步此原则，不再用案例成功、体积减少或 CI 数量替代功能契约。宿主对照和真人理解仍未完成，不能被这些程序测试代替。

## 13. 完整工程审计：把交付正确性与展示证据分开

**来源与背景**：2026-09-22，项目负责人要求完整检查、修复、实测、比赛材料和开发交接，并明确禁止擅自推送或提交。独立合成反例再次证明基线测试通过不能代表所有入口可靠：部分 Handler 丢失注释；目标检查异常后仍可正式交付；旧测试甚至接受把错误 CDS 降为 gene。

**处理：采纳并修正。** 输入解析与完整记录写出收敛到现有共享接口，预期从原任务和源文件重算；保留错误注释和原失败材料，纠正奖励错误行为的断言。未重造验证引擎。另明确专用 ConstructionTask 的序列/注释模型与实际 Recipe/Pipeline 制备流程的差别，以随计划绑定的 scope_note 告知能力范围。

审计同时改变证据口径：场景契约通过必须分开实际执行、部分分析和按设计阻断；Mutation/Coverage 必须指向真实实现，不能测旧转发文件；Trace 的同路径不等于同版本，文件存在不等于本次生成。打包改为审核过的源清单，并将外部序列/参考图与原代码许可分开。

实际解包进一步暴露了测试对外部材料的隐式依赖：仓库中通过，排除许可未确认的DNA后，多项必需Trace回归报缺文件。通用契约因此改用可公开合成输入，原外部反应另作显式集成保留。独立包测试与源码测试各自提供证据，不能互相代替。

收尾还发现缺失凭据和明确请求的官方检查可被跳过，旧交付清理可能触及并发产物。长期边界因此补齐：必需凭据不能省略，明确请求不能静默降级，每次交付只拥有并清理自己新建的临时目录。

**保留边界**：pET/Chr1 的原注释问题有来源证据，不能整体豁免；程序往返与独立用户理解、宿主决策质量、实验结果分别验证。Tianjin 的正式队伍与 Village 已核对，专属软件仓库、贡献与正式提交仍需团队动作。[审计](audit-report.md)、[最终报告](final-remediation-report.md)保存实证与未关闭项，不将文档准备说成比赛交付完成。

## 14. 完成标准纠正：文档数量与已知技术债不是收尾依据

**来源与背景**：2026-09-23，项目负责人指出“要求不止这么点”。上一轮虽有实质修复和30份文件，却在整体覆盖门槛未过时将仓库内可解决问题留为技术债，并提前进入简短教学。

**处理：采纳，重新打开原验收。** 进一步实跑旧预览发现快照说明晚于保存、旧文件混入交接、失败后旧候选仍在、缺失源未报告等问题；覆盖运行还曾主动减少场景。改为独立且不可覆盖的preview/delivery快照，保留实际失败诊断和来源状态，同一场景集接受覆盖统计。没有通过删除旧目标或调低阈值结束任务。

同时将开发文档从概述补为可接手的接口、数据流、状态、依赖、扩展和排障说明；教学需按原14节真正展开。只把账号授权、来源许可/真实材料、独立用户和实验等实际外部依赖留给团队，不能把尚可在仓库内处理的缺口混在其中。最终结果继续回写本轮计划与最终报告。

## 15. 交付与安装复查：验证实际使用版本，保留源问题

**来源与背景**：2026-09-30，项目负责人再次指出，把预填参数接入 Pipeline 的回归不能代表真实宿主使用；本轮选择先处理明显故障，宿主 Benchmark 另行验收。复查发现 Codex 仍安装旧提交，源码修复没有进入实际使用包，默认 Python 还指向缺依赖的另一环境。

**处理：采纳并区分证据。** 安装交接绑定包、源码提交和实际文件清单，并记录通过环境检查的本机解释器。固定路线的实际 CLI 执行继续用于代码回归，不能宣传为自然请求盲测。

独立反例证明酶切维护了另一套不完整的特征裁剪：保留片段却继续宣称完整 CDS 翻译或完整引物。改为复用已有裁剪契约，传递反应显式拓扑；明确的蛋白标签/切割位点不按完整蛋白要求终止密码子。完整翻译及错误遗传密码表的检查保留。pET 的两处细菌密码表冲突在可解释的注释副本中校订，原文件和 DNA 均不变；不向生产程序加入自动换表或批量修复 Chr1 的规则。

Windows 同目录竞争交付复现了权限错误的一种来源：胜出者已完成目录提升，另一尝试才执行提升。改为明确拒绝覆盖，保留胜出产物，仅清理自身临时目录。其他权限故障仍须独立定位，不能从此推断全部 Windows 访问异常已修复。实施与未决项见[交付修复计划](development-plans/workflow-delivery-fixes-v1.0.2.md)。
