## 我按什么顺序推进开发

**第2题实测后的P0调整：先补实际执行与交付闭环。** 2.0.2安装已核实，该轮制备与成品不一致、注释错位、交付版本不同步；重叠工具60 nt截断已独立复现。先修工具阻断，使调用与材料选择直接，再接通实际产物、共同核查和同版本交付。方案见[实际路径闭环](../architecture.md#p0实际执行路径与交付闭环)，本次为总结方案，运行改造未开始。

| 顺序 | 具体要解决的事 | 你能看到的变化 |
|---|---|---|
| **先保任务正确** | 原要求没有丢；最终引物对应实际模板；文件、注释和后续步骤一致 | 交付能继续用，换路线仍完成原任务 |
| **再让已有能力接顺** | 成熟流程能与单步工具衔接；保留完整材料、检查对象和元件/QC等角色 | AI能整段套用，也能混合操作，少手工搬运信息 |
| **让失败可处理** | 错误说清失败步骤和原因；保留已完成步骤的真实结果 | AI能补参数、换路或继续，不反复从头猜 |
| **最后减少浪费** | 合并重复来源重建，缩短默认返回，完整信息仍可读取 | 调用和阅读负担下降，必要检查保持 |

错误信息和方法声明缺口与P0闭环一起收敛；成熟流程组合及失败后继续先在实际链上打通，更多方法迁移按使用需求推进。重复计算和输出优化排在实际交付可靠之后。这周具体收敛范围见[架构方向](../architecture.md#流程复用与结构收敛方向)，成熟方法内部算法保持，不排新总工作流引擎。

一项修复结束，要有原失败、修复后的实际交付和独立正反例。受影响的公开入口通过后，按现有测试要求检查；发布候选再做完整包验证。测试通过不能代替原任务完成。

## 怎样判断软件已经有自己的闭环

选定演示任务须让使用者完成以下过程，并能打开其中的真实文件：

**给出要求和材料 → 检查已有材料 → 选择或复用流程 → 使用实际中间体完成计算 → 核对最终文件和原目标 → 看懂下一步。**

| 使用者应能做到 | 验收时看什么 |
|---|---|
| 不需要自己填一大张开发表单 | 从自然请求进入，关键缺失信息才澄清 |
| 复用成熟流程，也能根据失败调整 | 有实际方法调用和结果，不靠手工拼预期答案 |
| 第二轮继续用第一轮交付 | 实际模板、制备步骤和产物来源相符 |
| 找到可用交付 | 要求的文件、完整引物、准备和验证信息相互对应 |
| 知道哪些已检查、哪些仍未解决 | 不把候选、元件、QC或计算结果包装成已完成实验 |

九题按已有[五项评分规则](../question-bank/scoring-v0.1.md)检查：目标、制备、文件、验证、结论。适用的必需项全部成立才记整题通过。我对程序计算和文件作自动核查，你审阅关键要求；接管、校订输入、AI帮助及重复尝试分别记录。结果归入已知开发回归和本人使用测试，不宣称独立陌生用户评测。

## 同步准备给评委和未来用户看的材料

我从第1天准备Wiki内容骨架，测试完成一项就补入真实证据，你审阅后处理账号发布。先做以下5项：

2. **怎样安装和开始使用。** 一个受测包、一份短说明、一个真实入口。
3. **实际完成了什么。** 一个完整任务、一个多轮或失败调整案例，连接对应文件和检查。
4. **如何验证。** 分开写开发回放、宿主自完成、本人使用测试、AI/人工帮助和已有实验记录；外部试用若取得，另列。
5. **如何复用与扩展。** 一张简明架构图、现有接口、许可、标准文件与源码入口。

先整理已有实验记录。新实验按你实际时间另行安排；软件测试、可安装交付和Wiki整理继续推进。外部试用仅在有合适使用者时补充，当前不作为收尾门槛。你自己的使用记录如实标为本人测试；自动核查和AI评审不替代陌生真人证据。
