基线先跑一轮，修复后重测受影响任务，避免每天无目的地全套重跑。每题的时间/重试预算先记录，保留全部尝试。修复版和旧版分别记录，不把不同版本的成功拼成一轮成绩。第7天是收尾检查点，剩余阻断仍要处理并如实标注。

分工保持简单：**你定优先级、判断交付和协调提交；开发负责代码、核查工具与包；测试者实际运行；核查者对照原要求；Wiki/账号负责人整理页面并处理提交。** 这些是职责，不要求新增五个人。

## 开发按什么顺序做

| 顺序 | 具体要解决的事 | 你能看到的变化 |
|---|---|---|
| **先保任务正确** | 原要求没有丢；最终引物对应实际模板；文件、注释和后续步骤一致 | 交付能继续用，换路线仍完成原任务 |
| **再让已有能力接顺** | 成熟流程能与单步工具衔接；保留完整材料、检查对象和元件/QC等角色 | AI能整段套用，也能混合操作，少手工搬运信息 |
| **让失败可处理** | 错误说清失败步骤和原因；保留已完成步骤的真实结果 | AI能补参数、换路或继续，不反复从头猜 |
| **最后减少浪费** | 合并重复来源重建，缩短默认返回，完整信息仍可读取 | 调用和阅读负担下降，必要检查保持 |

已确认的错误信息损失和方法声明缺口可与测试并行处理。成熟流程组合及失败后继续，先选一条实际链打通；更多方法迁移按使用需求推进。重复计算和输出优化排在主流程稳定之后。这周具体收敛范围见[架构方向](../architecture.md#流程复用与结构收敛方向)，成熟方法内部算法保持，不排新总工作流引擎。

一项修复结束，要有原失败、修复后的实际交付和独立正反例。受影响的公开入口通过后，按现有测试要求检查；发布候选再做完整包验证。测试通过不能代替原任务完成。

## 怎样判断软件已经有自己的闭环

选定演示任务须让使用者完成以下过程，并能打开其中的真实文件：

**给出要求和材料 → 检查已有材料 → 选择或复用流程 → 使用实际中间体完成计算 → 核对最终文件和原目标 → 看懂下一步。**

| 使用者应能做到 | 验收时看什么 |
|---|---|
| 不需要自己填一大张开发表单 | 从自然请求进入，关键缺失信息才澄清 |
| 复用成熟流程，也能根据失败调整 | 有实际方法调用和结果，不靠手工拼预期答案 |
| 第二轮继续用第一轮交付 | 实际模板、制备步骤和产物来源相符 |
| 找到可用交付 | 要求的文件、完整引物、准备和验证信息相互对应 |
| 知道哪些已检查、哪些仍未解决 | 不把候选、元件、QC或计算结果包装成已完成实验 |

九题按已有[五项评分规则](../question-bank/scoring-v0.1.md)检查：目标、制备、文件、验证、结论。适用的必需项全部成立才记整题通过。开发者接管、校订输入及重复尝试分别记录；这组已知任务说明开发回归情况。

## 同步准备给评委和未来用户看的材料

Wiki负责人从第1天建立内容骨架，测试完成一项就补入真实证据。先做以下5项：

1. **软件解决什么问题。** 研究者给要求和材料，软件帮助形成可核查、可继续使用的设计交付。
2. **怎样安装和开始使用。** 一个受测包、一份短说明、一个真实入口。
3. **实际完成了什么。** 一个完整任务、一个多轮或失败调整案例，连接对应文件和检查。
4. **如何验证。** 分开写开发回放、宿主独立完成、人工帮助、用户试用和已有实验记录。
5. **如何复用与扩展。** 一张简明架构图、现有接口、许可、标准文件与源码入口。

先整理已有实验记录。新实验另按团队时间安排；软件测试、可安装交付和Wiki整理继续推进。外部试用由团队联系，首次用户试用优先验证使用闭环，不能当作严格陌生任务成功率。

Best Software关注标准互操作、验证、对其他项目的价值、外部集成、易用性和可维护文档，也要求开源许可及专属iGEM GitLab源码仓库。[官方公开奖项要求](https://competition.igem.org/judging/special-prizes)。页面和Dashboard的完整提交细则由账号负责人核实。
