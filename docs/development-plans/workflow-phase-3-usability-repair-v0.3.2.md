## 1. 问题基线与判断边界

原始材料保留在本机，不把用户 DNA、会话全文或模型中间自述复制到源码仓库：

| 材料 | 位置与用途 |
|---|---|
| 用户测试汇总 | `D:/document/第一次测试skill.docx`，含三组结果与用户反馈 |
| DSH 案例 | `D:/dshardness_workplace/cdc15-hyg/`，重点复现导出异常与大报告 |
| Trae 案例 | `D:/trae_file/6aaf6aa27084f97a7648be49/cdc15_hyg/`，方案网页、示意图、Trace |
| Codex 案例 | `D:/codex_project/skill测试/cdc15_current_review/`，简单核对任务与报告阅读缺陷 |
| 早期回答偏移 | `D:/codex_project/skill测试/cdc15_design/` 及该任务公开记录；中途已确认供体可用，最终改以停止提醒开头 |

上述是案例来源，不是任意环境都存在的测试依赖。实施时记录各宿主实际包版本、提示词、用户追加信息、模式及本地经验规则。原始用例不能取得时标明未复现；CI 用合成反例补覆盖，不冒充真实材料验收。

**已核对事实**：

- DSH 有三次 `Primer binding_sequence does not match template at [1224,1250)` 导出异常；“源模板坐标未平移到产物”仍是待复现的根因假设。
- DSH HTML 为 95,692,594 bytes，Trae 为 20,287,649 bytes，Codex 为 372,006 bytes。DSH 最大记录含较大的嵌套步骤对象，且 runs/audit_events/source_records/report 重复携带内容；不能直接认定为原始 DNA 字符串未省略。
- 三组明确交付清单分别有 10、2、1 个 untraced 项。`report.py` 将 handoff 状态直接加入科研 review，页面可能只显示裸状态；这不证明文件内容错误。
- `view.js` 有“查看本步原记录”的纯文字回退；通用 `formatted(raw)` 把 Schema、ID 和机器字段递归当作人类详情。
- 用户记录了首次回答漏交付 Trace 入口；同时认可主方案网页与替换示意图的实际解释价值。

**待验证假设**：Trace 提示负担影响主设计优先级；导出失败由坐标归属混淆造成；大对象可以通过减少派生副本显著缩小。不能从不同模型、宿主和追加信息的这三次测试推出因果或模型排名。

## 2. 本轮共同契约

1. 优先解决用户任务。先判断已有材料能否复用，以及是否需要新设计；“核对后无需重新设计”是完整结果。
2. 必要的生物学计算和真实冲突检查保留。供体结构、文件交付、最终细胞状态分别判断，不能把一层未知变成所有层的阻断，也不能掩盖确实改变行动的风险。
3. Trace 同时在代码和提示词上保持旁路。设计中记录事实与少量当时公开说明；完整组织与报告放在设计结论形成后。
4. 完整信息由数据层保存。报告正文和点击展开都服务于研究者，不把机器对象换个位置继续倾倒。
5. 原记录与失败案例不改写。修订、补录、后来的解释有独立身份；不把 untraced 改成伪造的成功来消除提示。
6. 保留现有三层和单一 Skill，不默认增加第二模型、服务、图数据库、通用治理框架或新的巨大验收矩阵。

## 3. 七项实施工作

### A. 主任务判断与首次交付

修改对象：SKILL.md 的工作流、相关 Recipe/经验规则指引及任务验收案例。必须检查宿主实际加载的规则，不能只改仓库的一份文本。

- 分为“核对并复用、制备已有设计、确需新设计”三种处理情况，不增加运行时枚举框架。优先利用用户明确给出的材料和目标；发现实际不匹配时再指出。
- “优先 Recipe”只适用于确需计算/构建的工作，不强迫已完成供体再经历设计、PCR 或组装。实体供体的制备与供体的重新设计分开解释。
- 回答顺序：材料结论 → 是否需要新设计 → 最短下一步 → 会改变当前行动的条件。已形成的重要结论不能在最终答复中被泛化提醒取代。
- 条件确实决定下一步时明确说明其影响；能独立完成的核对继续推进。不为“更谨慎”假定用户的文件无效，不承诺实际实验必然成功。
- 首次交付提供主结论、实际生成文件、必要的主方案/示意图，以及已生成的 Trace HTML/Markdown。用宿主支持的链接格式并检查目标存在，不列不存在的文件。
- 复杂结构可用直接服务于当前问题的方案图解释；简单核对不强制生成长 SOP。主方案与 Trace 互相引用，后者不替代前者。

验收：现成合格供体明确说明可沿用及不必新增的工作；真实材料冲突案例仍指出需要修改之处；未生成某类交付物时不声称已生成。不能只检查回答里出现了“无需设计”几个字。

### B. 分阶段加载提示词

修改对象：SKILL.md、references/evidence-trace.md，以及确有读取负担的经验规则/来源要求；程序验证保持原正确性要求。

- 主 Skill 常驻内容只包含完成任务、选择工具、必要验证、采集开关/共享目录及短指针。组织 Schema、报告编排、缺口修复流程放到明确的收尾分支，设计开始时不要求全文加载。
- Full 在真正关键选择发生时，随原设计响应留下简短理由与已用依据；不要每次调用工具都补一轮解释或整理所有字段。不存在的原始理由保留缺失。
- 主结论与产物形成后，读取对应快照和组织指引，提交 process/report_plan；后来解释不能改写成同期理由。必要的安全/正确性判断不延后到交付后才处理。
- 保持采集、组织完成度、科学问题三个状态独立。缺 Trace 解释或来源关联不自动进入 DNA gate，也不自动要求用户补实验条件。
- 先保留现有默认值作为对照；“日常默认 Observed”是待验证方案，不在没有结果时静默改全局设置。此次文档不更新 Codex/DSH 安装。

对照：在可固定模型、材料、用户信息、工具版本和额外规则的宿主中，先用“现成供体”和“确有冲突”两项任务比较 Off/Observed/Full，各至少两次新上下文。记录主结论、正确性、无必要的新步骤/追问、首次交付、工具轮次、耗时及可取得的 token；不可取得的指标写未知。此小样本用于定位和选择默认行为，不宣称统计意义上的普遍优势。另用固定设计参数做确定性的三档 DNA A/B，不能把两种测试混为一谈。

### C. 修复引物与产物坐标

定位顺序：scripts/run_recipe.py:write_preparation_artifacts → export_plasmid → core/tools/snapgene_io.py 的引物正规化/匹配；同时核对 core/tools/amplification.py 产生的 template、product、primer 字段。

- 用原三段路线复现，保存失败前制备行与实际源/产物；先判断错位来自传参、已有引物特征、坐标映射还是导出器，不能根据报错文字直接选定修复点。
- 明确每套坐标属于哪个记录。源模板绑定核心坐标、5′ 尾部和产物上的引物位置不能复用同一个未标明坐标空间的区间。
- 在实际错误产生处修复并更新受影响调用方。保留完整 oligo、链方向、跨原点和连续 PCR 中间体关系，不删除引物或 source features 换通过。
- 同时检查源图标注与产物导出；成功后以保存文件读回，而非仅检验内存中的对象。

验收：原路线通过公开 Recipe CLI 完成原先失败的 .dna 导出；独立确认目标序列、完整引物、结合核心与坐标匹配。覆盖有尾/无尾、正负链及相关跨原点/后续扩增场景；只补与实际修复有关的回归。

### D. 分清验证对象与结论范围

修改对象：实际触发问题的 Recipe/Task 结果分类、Core 检查作用范围与经验规则；不预设必须重建 gate。

- 区分本次只检查的既有供体、制备产物、模拟整合位点、验证设计和完整构建。不能为了调用成功而把产物改标成不相关类型。
- 将每个失败关联到真实被检对象、区域和条件。对继承注释错误比较输入与输出，核查是否跨编辑区及是否影响当前交付；“离编辑区远”不是自动豁免理由。
- 生物学未知不自动改写成序列错误；也不能将序列/结构通过解释为细胞可存活、功能恢复或全基因组唯一。
- 如需改变现有阻断范围，先明确原本检查什么、为什么对本次产物不适用，并保留真正失败仍阻断的反例；不得直接把 FAIL 改成 PASS/N/A。
- 承接前序 pET 注释阻塞的作用范围诊断。可在本轮证据充分的边界内修复；无法正确消除的阻塞保留，不用更换输入或降低标准换取“可发布”。

验收：既有片段核对不被升级为未授权的细胞存活审批；要求精确删除、错误方向/接头或真实 CDS 破坏的任务仍得到正确判定。无全基因组检查不写“不会脱靶”，物种外推不写成该菌株直接实验结论。

### E. 后续操作采集与交付清单

修改对象：evidence_trace/runtime.py、intake.py 及实际独立工具调用入口。

- 保留七入口，针对本轮临时脚本和直接工具调用补一个可复用的薄观察入口。优先复用 observe_files/现有工具注册；具体入口按复现选定，不新增一套通用代理执行框架。
- 在调用前记录实际输入和文件版本，调用后记录返回、明确输出及其身份；异常保留部分结果。调用结果只有确为 Core 检查时才能成为 Validation，普通脚本成功退出不是生物学通过。
- 文件复制、转换、人工/AI 撰写的方案文档各有正确身份。可如实记录从现在开始观察到的写入；事后发现文件只能记录观察，不能补造历史生成动作。
- handoff 验证整份实际交付清单。能从本轮捕获的操作追溯的文件应 linked；既有来源未知文件仍保留 untraced，并说明具体文件、缺失关系和影响。
- 仅记录不完整时使用独立的“记录完整性”入口，不进入科研待办。文件实际缺失或当前版本不是已验证版本时，既显示交付问题，也保留其技术原因。

验收：完成修复后的真实流程首次交付清单涵盖所有新文件，生成/复制/转换可回查；故意仅导入旧文件的反例仍不得被洗成已追溯。对研究者说明缺什么记录，而不是裸露状态码。

### F. 大对象保存与报告体积

修改对象：snapshot、project/assemble、build_report、render；先按实际各区段/字段计量，不先引入压缩库或缓存服务。

- 原 events.jsonl 与输入案例只读保留。先减少派生结果中的大对象副本，让运行、节点、来源和报告通过现有 ID 引用同一份事实，避免 report.sources 再携带完整 raw data。
- HTML 内嵌人类阅读投影和所需详情，不再内嵌整个 graph/audit/runs 多套结构。原始 JSON/日志通过独立技术文件入口访问，仍能离线使用；不能依赖浏览器对 file:// JSON fetch 的跨域许可。
- 如果需要改变大字段采集方式，再设计明确的省略或外置引用：内容去向、版本、缺失状态必须可解释。不能直接截断证据、抹掉旧失败或宣称压缩后仍保留了实际已丢失的信息。
- 优先保持事件格式兼容。派生 graph/report 若改字段，用明确版本和迁移说明更新 CLI、文档、消费者及旧日志重建测试，不同时维护两套默认报告。

验收预算：使用上述 DSH/Trae 原日志重建的新默认 HTML，分别不超过 5 MiB 且不超过原文件的 10%；这是本轮工程目标，不是已实现结果。相同环境下记录冷打开和首次详情可用时间，目标不超过 3 秒。完整记录仍可定位、同一日志重建稳定、离线断网可读；图层不得靠删步骤达标。

### G. 报告层全面重做人类详情

修改对象：report.py、view.js、view.css、Markdown 导出和有限的报告数据契约。沿用已认可视觉方向，不再重新发明版式。

- 正文与默认展开均使用明确的人类阅读字段。formatted(raw) 只允许留在独立“技术记录”；不能作为缺少可读详情时的默认退路。
- 选择详情回答：做了什么选择、理由来自谁、依据支持哪个方面、限制、关联步骤/产物。文件详情回答：用途、实际来源、生成步骤、对应检查及交付身份。证据详情回答：来源、相关片段、当前用途与适用边界。
- 内部 ID、Schema、哈希和事件号继续用于关联，默认不作为正文内容。不能通过把字段名翻译成中文就保留同样的机器对象堆叠。
- 建议在现有 report 投影中增加按引用索引的人类详情对象；内容只从已有记录/组织取得，普通未知类型写清缺少哪类说明，保留技术入口，不自动补科学解释或新调用模型。
- 清楚区分节点主对象与支持依据。若当前“source_refs 中有任一类型便通过”的约束鼓励硬塞 R1/D1，允许增加一个明确主对象引用并提供旧记录兼容；不是扩充一套节点系统。来源材料和证据可作为旁支，不必伪装为要求/选择。
- 所有“查看”文案必须有真实操作和目标。没有目标写成陈述，如“未记录本步输出关联”；不能显示假链接。多个文件/检查能按可理解名称区分，不堆相同的“文件记录”按钮。
- 图文选中状态保留序号、类型、名称与上下游关系；不把主任务答案变成数据审计说明。科研待办、文件交付问题、记录缺口分别显示。

验收：不打开技术记录，陌生研究者能说明所选决定、依据边界和文件用途；可以从实际文件回到生成/检查。默认详情不出现机器字段清单、裸 untraced 或无效入口。HTML 与 Markdown 含义一致，简单任务自然结束，不强制凑六步或固定几项选择。

## 4. 实施顺序与交接

1. 固定原始基线，补导出故障最小复现；写下主任务和报告的具体错误表现。
2. 实施工作项 A、B、C、D：先修任务判断、提示负担、产物正确性和检查范围，再运行真实设计。宿主提示对照和固定参数的文件 A/B 分别记录，不能互相替代。
3. 执行 E/F：接上真实后续操作，消除重复数据，并验证原日志兼容与文件身份。
4. 执行 G：从已保存数据生成正文与人类详情，使用真实任务做交互和理解检查。
5. 复跑相关回归及全量适用检查，独立包验证。更新计划、Spec、History 与限制；commit/push 到指定开发分支并核对对应 CI。

每步可小批提交，不要求一次改完所有文件。阶段顺序为实施建议，必要调整须说明依赖与证据；不能拿报告好看代替主工具成功。

## 5. 完成标准与前序事项处置

| 事项 | 本轮处置 |
|---|---|
| 三层、旁路、追加历史、实际验证与候选身份 | 保留；优化关联和表示，不重建安全核心 |
| 引物导出、单纯要求被包装成决策、主结论被提醒覆盖 | 本轮直接复现并修复 |
| 原 pET/Chr1 注释问题 | 承接影响范围诊断；符合证据的修复纳入，未解问题必须单列 |
| 先前三档 DNA A/B、旧日志、Windows/非 ASCII | 继续作为回归，不重复计算历史通过数 |
| 模型提示干扰、发布默认模式 | 用受控对照决定；证据不足时保留未决，不伪造因果 |
| 静态原型已获意见、真实页面独立理解未验收 | 沿用有效意见；新的默认详情必须用理解问题检查，不强迫用户先理解 JSON |
| 自动捕获全部宿主行为、宏观安全论证、wet-lab 性能 | 不纳入本轮承诺；明确实际范围 |

交接时分别报告：哪些已实现、哪些实际验证、哪些尚待人反馈或外部条件。不能仅以单测总数、组织 current、日志 complete 或自评分宣称“所有任务可发布”。用户 DNA 与原输出留在本机；可公开的合成反例进入测试。本轮不更改全局采集模式，也未更新已安装的 Codex/DSH 包。
