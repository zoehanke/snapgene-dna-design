# Evidence Trace：人类阅读与界面规范

r14，2026-09-20。当前阅读规则的唯一来源；设计转向原因见[项目历史](../history.md)。旧实现见 Git 历史及 [Phase 3 记录](safety-phase-3-change-impact-v0.3.md)。组织/编排接口及固定 renderer 已实现，但默认详情、大文件与任务表达仍有实测缺陷；下述新增阅读契约按[实用性修复计划](workflow-phase-3-usability-repair-v0.3.2.md)实施，不视为已通过验收。

用户参考图对应的[视觉设计文稿](evidence-trace-report-visual-design-v0.3.1.md)细化本轮独立示意：深色紧凑侧栏、白色章节表面、首屏三列结果摘要、任务章左右布局。报告语义仍以本文件为准；图文与手机状态须保留。正式 renderer 已消费真实组织数据，不保留示例中的固定决定数量或故事。原型的视觉认可不等于真实页面理解验收。

[安全 spec](../../specs/safety-module.md) 定义事实边界，[当前计划](safety-phase-3-readability-v0.3.1.md) 定义实施与验收，[Reader Demo](safety-phase-3-reading-draft.md) 提供具体样稿。实现阅读结构前还须读 [标准空白框架](evidence-trace-reader-template.md)：本文件定义阅读规则，框架定义可选结构，案例检验填入后的效果。结构或显示规则变化时同步相应文档，不重复整段规范；完整框架不代表栏目必须全部出现。此文件不作为宿主运行时生成网页的提示词。

数据接口见 [数据层到阅读层映射](../../references/evidence-trace-reader-mapping.md)。底层 reader 提供事实与旧日志支持；正式 HTML 消费完整组织结果的 report 投影，原记录留在详情引用中。关系必须区分声明依据、修订、调用阶段、材料引用和实际生成，不能把普通排序画成因果线。

## 为谁服务

目标输入见[三层设计](safety-phase-3-three-layer-design-v0.3.1.md)：数据层形成完整 design_process，另有 report_plan 在下述固定格式内提供阶段分组、摘要、短标签和展开建议。报告不能首次发明研究逻辑。AI／人确实参与编排，可与数据组织同次输出；固定渲染、导出和交互不再次调用模型。

每个摘要、图中步骤和重要解释须能回查完整过程及原记录。初始收起不删除数据；未归类材料仍可查。编排绑定确切组织版本，新增事实导致旧组织陈旧时明确显示范围，不能把旧摘要套用到新产物。程序固定保留文件角色、原检查状态与影响当前判断的未解决问题。

默认页面服务于未参与设计、具备基础生物学知识的研究者。让他不展开审计信息也能说明：用户想做什么，谁做了哪些选择，依据是什么，程序查了什么，最后得到什么。

理解优先于默认展示完整。每条信息先问“帮助理解哪个研究问题或决定”；每个栏目先问“本任务是否真实存在”；每条关系先问“记录是否支持”。不满足就不默认展示，但保留底层事实。

## 默认报告格式：research-report-v1

所有新报告默认采用同一个版本化格式，不要求用户选择模板或学习字段。AI 填写内容，程序固定一级栏目、顺序、步骤标签、实际状态和详情入口；不接受 AI 自定义顶层栏目、HTML、CSS 或任意布局。语言可本地化，栏目职责不变。此规则只约束报告，不限制设计方法、决策类型或完整数据。

### 固定外框与栏目

页首为任务标题、任务摘要，以及“得到什么 / 已验证 / 尚不确定”的结果概览。概览引用实际结果及记录缺口，不输出含混的整体 PASS。Document / Mind Map / Split 切换位于设计过程章的标题旁，不再另设顶层控制栏。标题由作者提供；范围、演示身份、陈旧或不完整记录提示由程序在相关位置显示，不伪装成最新完整报告。

| 顺序与固定标题 | 默认内容 | 出现规则 |
|---|---|---|
| 1. 我们要做什么？ | 已知任务目的、用户要求、影响选择的材料/条件；简述 AI 与程序实际参与 | 始终出现；小任务合为一段，缺目的写“未记录任务目标”，不猜背景 |
| 2. 设计怎样形成？ | 已整理的关键过程，按阶段分组、按实际关系展示分支；每个步骤使用统一格式 | 始终出现；没有 AI 选择时呈现要求和程序结果；未整理时明确为有限事实记录 |
| 3. 本次得到了什么？ | 产物入口与实际角色、关键检查的对象/范围/结果；无产物时说明实际进展 | 始终出现；不将“未记录产物”推断为“未生成”，不捏造成功文件 |
| 4. 现在需要处理什么？ | 当前真实未决、阻塞、已要求但缺失的检查或有依据的复核事项 | 条件出现；无事项时整个栏目消失，不显示空表或泛泛建议 |
| 5. 查看详细记录 | 完整步骤、来源原文、程序返回、历史、未归类材料与原始事件入口 | 始终可达，默认收起；Markdown 放文末附录 |

第一节首次说明 Trace 用途：“这份记录区分用户要求、AI 的公开选择和程序检查，便于复核设计依据；不作安全裁决，也不展示隐藏思维。”不在各节重复。模拟或回放案例在页首标明，来源细节下沉。

任务背景和用户约束在第一节交代；后续只有发生修改、形成新取舍或理解某步骤确有需要时再出现。不将同一句请求复制成多段正文。产物可作为过程终点出现，文件入口和检查摘要集中在第三节，互相引用而不复制整表。

### 每步固定结构，内容条件出现

1. 标题：`编号 · 类型前缀｜具体动作或发现`，前缀沿用下表四类；编号用于阅读定位，不证明时间或因果。
2. 正文：一至三句说明“发生了什么、作用于什么”；程序结果还需明确检查范围，产物明确候选/中间/正式身份。
3. 选择旁支：有说明时默认一句理由并标明来源；有依据时默认一句“依据是什么、支持哪个方面”，附可直接打开的来源；影响当前判断的限制/冲突默认可见。
4. 详情入口：统一“查看理由与依据”或“查看程序记录”，展开具体条件、引用原文及版本。没有内容时不生成空入口。

长度是写作目标，不作自动截断或删证据规则。无法在短句中保持原意时保留必要文字，其余放详情。原始理由缺失不强制 AI 补写；需要解释该缺口时显示“未记录当时理由”。来源标签区分“用户说明 / AI 当时说明 / 根据记录整理 / 后来补充解释 / 来源未确认”。

默认依据摘要按“材料或来源报告了什么 → 与当前选择有什么关系 → 重要适用边界”书写；相关内容才出现。不能只留“有证据”按钮，让读者必须展开才能理解基本理由。

### 结果、待办与详情的固定表达

- 产物：名称、用途/组别、实际交付角色、文件链接；版本区别只在容易混淆时露出。缺失文件不能保留正常下载入口。
- 检查：对象、实际检查范围、具体结果及原记录链接。一次检查只说明其真实范围；结果区可链接过程中的检查，不重新复制为多份证明。
- 待办：问题、为什么影响当前目标、关联步骤、已有建议行动。没有已记录的建议时只列问题，不让 renderer 临时生成科学建议。与同一问题有关的多条记录聚合展示。单纯 untraced、说明缺失或报告未整理进入“记录完整性”，不自动成为科研待办；真实缺文件或验证版本不对应仍作为交付问题显示。
- 详情：点击展开仍是报告层，按对象解释意义、依据、限制和关系。原始机器数据进入独立“技术记录”，不能作为默认详情的兜底实现。

### 默认展开内容的职责

| 点开的对象 | 应回答的问题 | 默认不展示 |
|---|---|---|
| 设计选择 | 选了什么；理由来自谁；依据支持哪个方面；限制；影响哪些步骤或文件 | 决策 JSON、内部 ID、字段枚举、采集元数据 |
| 文件 | 是什么、做什么用；候选/QC/正式身份；来自哪些材料和动作；实际检查了什么；能否取得文件 | 路径与哈希清单代替用途说明、把关联检查冒充全文件证明 |
| 证据来源 | 来源名称和入口；相关片段；如何用于当前判断；适用条件与边界 | Source/Statement/Claim 原始对象树 |
| 程序检查 | 检查对象与范围；具体结果；哪些部分未执行或未知 | 全部返回值递归展开、孤立 PASS/FAIL |
| 记录缺口 | 哪个文件或步骤缺哪段记录；影响的是可追溯性还是交付；已有可回查材料 | 裸 untraced、要求用户理解内部状态码 |

只显示实际有内容的条目。生物学坐标、具体文件版本等确实帮助判断时可展示；这里限制的是机器元数据堆叠，不是删除有用技术事实。完整数据留在数据层，技术入口可读原 JSON/日志，但研究者不打开它也应看懂主线和默认详情。

来源缺失不能靠新解释补齐。未知记录类型应明确“尚无可读说明”及对应对象，不自动调用模型，也不将所有字段塞回侧栏。多个同类来源使用可区分的名称；所有“查看”必须可操作，无目标时改为明确陈述，不制造假链接。

### 阅读体积与离线使用

HTML 仅携带阅读投影、实际可读详情和关联索引；不将完整 graph、日志、运行数据和来源副本重复嵌入页面。技术文件可独立提供，但默认正文和详情离线可用，不依赖联网或本地文件 fetch 例外权限。去重、外置或省略必须保留事实去向及历史引用；不靠截断证据达成体积目标。

### 图形模式采用同一格式

Mind Map 以任务目标为根，关键阶段沿纵向排列，实际并行方案分列。步骤沿用正文编号、类型和短标题。理由、依据、限制挂在所属步骤，默认收起；关键未决提示仍可见。阅读次序用编号/空间位置表示，只有已有关系才画带含义的连线。AI 不能用 reading_order 创建依赖。

Document 显示上述正文；Mind Map 将第二节换为占主要空间的全图；Split 使用同一图和右侧所选步骤详情。目标、当前状态、结果入口和必要待办在三种模式中均可达。小屏 Split 切成图/详情标签，保持选择和展开状态。Review 仅是第四节的集中入口，不建立另一份报告。

### 格式验证与可读性验收

程序检查 profile、一级栏目由固定代码产生、引用可解析、步骤标签和来源标签合法、实际状态未被编排覆盖。数据未整理或缺编排时仍使用这个外框，写明“尚未整理”，显示可获得的事实，不以自由生成网页补救。

人工用简单成功、分支比较、修改后待执行、失败未交付四种实际记录检查：不展开详情能否说明目标、关键取舍、主要依据、实际检查和结果身份；未知部分是否明确。重大阅读结构变更宜先用代表性静态稿或交互原型获取反馈，复用已有有效意见；已获授权的修复不因等待重复试读而停工。格式检查与真人理解分别记录，不以模板齐全代替可读，也不把缺少反馈写成验收通过。

## 上下文与主链

开头用短正文交代研究/任务背景、为何做设计、用户当前要求、AI 和程序各自参与什么以及 Trace 的用途。小任务可以合为一段，不要求四张卡片或四个栏目。缺背景不能从参数猜出项目故事。

主结构是 **任务背景 → 设计形成过程 → 本次结果**。主链只放推动选择、改变方向、解释关键材料或交付所必需的事件，不是完整运行日志。

| 阅读步骤 | 表达方式 |
|---|---|
| 要求 | 用户目标、约束、明确修改；原话与宿主摘要区分 |
| 选择 | 用户/AI/未知选择者；遵从明确要求不包装成 AI 自主取舍 |
| 程序结果 | 区分发现、计算和正式检查，说明实际范围 |
| 产物 | 关键中间体、候选、最终文件；同名文件带变体/版本语境 |

步骤标题统一采用 **`编号 · 类型前缀｜具体内容`**。前缀固定，正文自由：要求用“用户要求”；选择用“用户选择 / AI 选择 / 选择者未记录”；检查、发现和计算统一用“程序结果”；文件用“中间产物 / 最终产物”。例如“01 · 用户要求｜确定比较组”“02 · 程序结果｜核对来源”“03 · AI 选择｜采用顺序制备”。不要把某类前缀省略并混入标题正文。用户明确指定的约束归“要求”，真实取舍才归“选择”；仅有人工/文献核对而没有程序依据时，不冒标“程序结果”，应保留为有来源的事实旁支。

静态 Markdown 样稿只用标准标题、段落、引用和链接。详细内容放可跳转的附录，不嵌入 HTML 折叠标签；未来 HTML 的折叠由固定 renderer 实现。类型标签和参与者需要一致，句子不必套固定话术，也不要求每种类型都出现。

用户确认归于对应要求/选择；待办附着于相关步骤。四类是阅读组件，不扩展底层科学节点体系。例行读取、每次工具调用、参数碎片、ID、哈希和原始 JSON 下沉详细记录。

## 决策旁支

主链步骤写“谁做了什么”；理由、依据、限制附着在相关选择旁，不各自挤成一串主链节点。

- 理由：选择者实际留下的公开说明。Document 默认可露出一句；缺少就不补造。
- 依据：相关用户约束、输入事实、程序结果、论文或数据库。多条细节折叠，保留其具体支持方面。
- 限制：该依据不能推出什么；重要冲突/限制默认简短可见，详细条件折叠。

替代方案和下一步行动只在已记录且有用时出现。Mind Map 默认折叠理由/依据旁支，选中后展开；不能把折叠变成隐藏关键失败或冲突。

来源用“用户说明”“AI 当时说明”“未记录原始说明”“事后辅助解释”表达。旧来源不充分时写来源未确认。机器字段仍在详情，不要求研究者理解 actor 或 mode_at_capture。

## 条件性内容

| 内容 | 何时显示 |
|---|---|
| 用户修改/否决/确认 | 有明确用户来源及对应对象 |
| AI 理由 | 有真实说明；Full 关键选择缺说明时提示其具体缺口，Observed 不强求额外说明 |
| 证据/限制 | 存在对应材料或影响理解的证据边界，不强制论文链 |
| Change Impact | 有变化及关联影响，挂到实际受影响步骤 |
| 待复核 | 用户目标未被回答，或有具体证据缺口、未处理影响、人工判断项；写清对象与行动 |
| 待实验回答 | 当前用户目标涉及计算无法回答的科学/性能判断 |

简单任务可以结束在已交付文件，不生成空栏目或泛泛的实验担忧。缺失已要求的检查、失败及重要冲突必须保留；“未要求”不改写成“检查失败”。同一次程序检查按实际作用范围展示一次，不复制到所有 Decision 下暗示全面证明。

## 三种视图与顺序

Document 纵向阅读同一过程；Mind Map 图形化看整体与分支；Split 左侧完整图，右侧选中步骤详情。三者共用数据、步骤选择和展开状态；用户修改或程序发现也能选中。Review 只看当前具体待办，无待办时不占主要入口。

以可证实的执行、材料和修订关系为骨架，研究逻辑作分组，记录顺序作补充。参数可能在工具返回后才被观察，追加时间不等于选择发生时间。并行变体并列；只有明确关系才标“导致/因此”，普通先后不能冒充因果。晚补说明挂回原步骤并保留补录身份。

详细来源、定位、版本、内部 ID、哈希、原事件、完整 Artifact Trace、Advanced Graph 和 Audit Log 统一收在“查看详细记录”。主线保留结果身份和可打开的产物入口。

## 语言与视觉

每节回答一个与当前任务有关的问题。专业词首次出现解释其意义，而不只展开缩写。使用已有文本和受证据约束的固定表达；renderer 不凭突变名称、参数或论文题目自动生成科学理由。

Reader Demo 开头一次说明：“它记录关键选择及依据供人复核，不作安全裁决，也不展示 AI 隐藏思维。”模拟对话与回放结果一次清楚标记，内部案例来源放详情，必要的未执行状态不能隐藏。

冷灰白、细线、清晰版心与留白；正文约 15–16px、行距约 1.7。等宽字体仅用于确有必要的标识/坐标。用来源文字配少量语义色，不依靠颜色区分角色。不设 KPI 卡片墙、渐变或装饰性网络。键盘、窄屏、离线与 reduced motion 支持保留。

## 正反例

- 不写“论文支持先做单突变再做双突变”。写“论文支持研究该候选；顺序制备是为保留比较材料作出的路线选择”，并分别提供依据。
- 不写孤立的“Validation PASS”。写“程序检查到编码区无提前终止且保留末端终止；独立目标检查未请求”。必须取自实际结果，不能把整质粒摘要误用于某个 CDS。
- 不写每个任务都“还不知道会不会表达”。仅当用户目标涉及表达表现时列为待实验问题；仅交付构建的任务可在准确说明检查范围后结束。

## 验收

Reader Demo 场景、静态理解、浏览器可达性和真实页面理解分别验证。采用哪种原型、先验证哪项，应结合变更风险和已有授权决定；不把某一历史实施顺序变成全部 renderer 修改的前置审批。没有真实反馈，不能声称真人理解已通过。

不展开详细记录，读者应能回答任务目标、用户/AI 取舍、具体依据范围、程序实际检查和产物身份。问理解问题，不用好看或字段齐全代替。5/15/30 秒用于记录定位效率，理解错误必须修稿；不能用压缩文字制造漂亮数字。两名试读者的原回答与耗时保存在计划的验收记录中，不另建 benchmark 系统。
