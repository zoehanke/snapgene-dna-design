## 给项目负责人的简要说明

本轮把“每个 Decision 展示全部内部信息”改成“任务背景 → 设计形成过程 → 本次结果”。用户、AI、程序和关键产物在同一过程中出现，理由/依据/限制挂在相关选择旁。简单任务自然结束，复杂任务按真实分支和修改展开。

记录系统、已有条件证据与 Change Impact 继续使用。人类理解优先于默认展示完整，但不删原始事实。先试读静态稿，再改页面，避免再次用工程绿灯代替读者理解。

## Reader Demo 与工程案例

- 工程回归使用 [GFP +3 bp](safety-phase-3-engineering-case.md)：验证长度变化、旧/新检查、影响和文件追溯、开关一致性。它不承担主要 UX 证明，旧试读请求已作废。

- 静态稿明确“模拟对话 + 已有程序记录回放”，程序结论只取自可核查结果；不能把回放说成新执行。可执行 Reader Demo 阶段再通过现有入口完整重跑，记录当次输入、选择说明和真实输出。
- 不强求用户否决情节。若增加模拟修改，先明确标注、实际提交并推进运行；不重写旧事件来配故事。
- 原结果中三份 clone 的 `goal_check.status` 均为 `not_requested`，不能把编码区检查通过概括为整个请求都已独立验证。可执行演示需按新请求准备明确检查，并显示真实范围。

## 验收方法

### 真人静态稿与最终页面

由两名未参与本次设计、具备基础生物学知识的读者分别阅读。静态 Markdown 先读主链、不跳转附录；最终 HTML 默认详情收起。主持人不解释内容。要求正确回答：任务目标；用户规定了什么；AI 哪些选择仍有取舍；文献支持哪个方面；程序实际检查什么；最终文件属于哪个变体。

理解正确是硬门槛，5/15/30 秒作为目标定位时间单独记录，不作为压缩必要信息的理由。保留稿件版本、原回答、耗时、卡住位置和修订结果。误把回放当新运行、用户要求当 AI 选择、论文动机当制备路线证明或程序检查当表型/安全证明，均须改稿再试。

- 案例适用性：2026-09-12 用户明确确认，保持有效。
- 静态稿第二步：2026-09-13 用户原话“第二步我觉得可以了”，记为项目负责人审阅通过。当前草稿的用户未提交修改保持原样；验收依据是此次明确确认，不是模型推断。
- 双人理解题原回答、定位耗时：未提供，不补写、不声称目标达成；最终页面仍需单独验证理解效果。
- 最终页面真人试读：未开始；需在实际 renderer 上另验。

### 工程与交互

| 场景 | 要检查的行为 |
|---|---|
| 简单构建 | 要求、处理/检查、产物可自然结束；没有空论文/修改/实验待办栏目 |
| Observed | 已有用户理由保留，无额外 rationale 不当成程序故障；实际参数不冒充 AI 自主选择 |
| Full | 保留原短说明；目标增加阶段/交付前的宿主 AI 组织与报告编排，可同次响应提交；记录真实成本，不在 renderer 中另起模型调用 |
| 多分支/修改/重试 | 并行不是先后依赖；未成功路线不冒充交付；同名产物有明确身份 |
| 原说明/晚补说明/旧日志 | 来源不混，补录不抹掉原始缺口；缺背景不能自动编出研究故事 |
| 检查与影响 | 检查按真实范围展示，不复制出全面证明；变化建议不执行重算或更改原 PASS |
| 三档真实入口 | Recipe、Pipeline、ConstructionTask 的 DNA、拓扑、注释、引物、制备、Validation 意义和正式文件保持一致 |
| 浏览器 | Document/Map/Split 共用步骤/分支选择；离线、键盘、窄屏可用，重要来源与产物可达 |

复用已有真实输入、回归和多证据案例，增加与上述行为直接相关的测试。不做大型 UX schema 或 golden benchmark，不用历史测试数量代替本轮结果。

## 第三步实际实现与交接

- 用户来源：Requirement 可带 requirement_source、原文/摘要形式及已有 context；change/confirm/reject 需来源和确切 basis_refs。记录提交者不等于原始说话者，旧来源保持未知。
- 阶段：stage_started 的事件 ID 作为 stage_ref，关联返回、失败与输入观察；返回后观察明确标注 accepted_inputs_after_call。派生阶段保留原始事件 ID、序号和记录时间，不制造真实选择时刻。
- 关联：Decision 与补充解释可引用确切节点版本或事件。现有 trace-input 可显式选择 context_refs，依赖仍保留但不把所有依赖中的旧 Decision 当作本次活跃决定。默认沿用 latest_records 并明确标注。
- 实际检查与文件：新增 result_event_ref 回指本运行的真实返回事件；同运行关联明确标为 same_run，仍不能作为某个 Claim 或序列区域已被验证的证明。
- 缺口：issues 只表示日志/引用/采集故障及未完成运行；coverage_gaps、explanation_gaps、association_gaps 分开。Observed 无额外说明、缺少强制 Claim、未请求检查不再自动生成检查失败。真实失败和证据问题仍保留。
- 用法见 [使用说明](../../references/evidence-trace.md)；同步 SKILL 和两个 spec。没有新增依赖、哈希机制、会话系统或程序结果生成器。

## 第四步实际实现与交接

数据层与阅读层的完整对应表见 [映射文档](../../references/evidence-trace-reader-mapping.md)。它是接口说明；design.md 继续保存阅读规则，标准框架继续保存可选结构，不新建重复 UX 规范系统。

- 新增纯函数 reader.py：从现有图、条件证据、运行及阶段记录派生 context、steps、runs、relations、review 和 diagnostics。Requirement/Decision 对应要求/选择；检查与有意义的程序发现合并进过程；Source/Statement/Claim 留在对应选择的依据旁支。
- 一次返回的检查只显示一次。未请求检查不生成空步骤；普通 partial/unknown 适用性保留为条件边界，不每条变成待办。失败、明确反对关系、缺失判断依据与变化问题按步骤聚合。
- 多格式文件只在同运行、角色、目录、名称与生成事件相同时合并；同名不同生成记录仍区分。无正式交付时可显示已有候选；不会把候选升级为正式产物。
- 复用现有路径与内容锚点识别材料引用；多匹配只记歧义。历史输入材料在运行筛选时放 related_steps，明确 reference_only，不算本次新产物或新检查。
- 运行筛选同时过滤证据、后补解释、变化和每条待办。未关联的参数按调用形成程序输入事实；内容相同的不同调用保留独立观察。排布锚点使用 anchor_sequence，不冒充实际发生时刻。
- 增加只读 `trace_design.py reader --trace-dir ... [--run-id ...]`，正常派生 graph.json 同时含 reader。没有新事件、模型调用、哈希机制或依赖。
- 旧 chain_views 暂留给尚未修改的 v0.3 HTML；reader 是第五步的统一数据入口。第五步切换后淘汰旧六栏/单节点 UI 及相应旧阅读依赖，不长期维护两套默认阅读逻辑。
