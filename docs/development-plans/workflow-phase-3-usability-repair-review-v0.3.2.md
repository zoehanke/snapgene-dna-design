# 主任务与 Evidence Trace 修复方案人工检查版

r1 · 2026-09-20 · 这是待实施方案，不是修复完成报告。

[开发版](workflow-phase-3-usability-repair-v0.3.2.md)负责代码位置、接口和测试细节。本版解释改什么、为什么改，以及你怎样判断它是否有用。

## 1. 这一轮真正要达到什么

先让 Skill 把用户的问题解决清楚，交出正确可用的文件；再让 Evidence Trace 帮人理解这件事怎样完成。检查和记录都服务于任务，不能反过来让简单任务变复杂。

这轮测试已经证实文件导出错误、大报告重复、来源缺口混入待办、详情难懂等问题。“Trace 提示词让模型偏离任务”有迹象，但还不是已证明的唯一原因；不同模型、宿主、额外规则和用户补充信息也不同。

## 2. 七项改动及你应该看到的效果

| 改动 | 为什么 | 用户应看到什么 |
|---|---|---|
| 主任务结论优先 | 已有供体可以复用，却被回答成仍需一串前置工作 | 先告诉你能否沿用、是否需新设计、哪些工作不用做，再给必要下一步 |
| 减少设计阶段的 Trace 指令 | 同时设计和填完整证据链，可能分散注意力 | 设计时只做必要计算和简短选择说明，完整报告在结论形成后整理 |
| 修复引物导出 | 有实际 .dna 导出失败，不能只交内存中的结果 | 同一原案例可正常导出，文件内完整引物和坐标正确，原有注释不被删掉 |
| 分开不同层次的检查 | 供体结构、细胞存活、文件来源被混为一谈 | 清楚说明哪项结论成立、哪项未知、到底影响什么，不一概拒绝或一概通过 |
| 补生成记录和交付入口 | 文件确实生成了，却查不到过程，首次还漏报告链接 | 新文件能回到实际生成步骤；第一次回答就能找到方案、产物与已生成的 Trace |
| 减少重复数据 | 一个报告达到约 96 MB，影响打开和查看 | 报告只加载阅读需要的内容，完整证据仍能找到；历史不会为缩小文件而丢失 |
| 重做每种展开详情 | 点开仍是 ID、Schema 和状态码，读者无法复核 | 点开选择看到理由与依据，点开文件看到用途、来路和检查，点开证据看到相关原文与边界 |

## 3. 主答案应该怎样改变

以现成供体为例，先判断提供的结构是否满足当前目标。满足时明确说明“可以沿用，不需要重新设计同源臂”；需要制备实体 DNA 时，再说明制备方式，不把“制备”说成“设计没有完成”。

若真实发现结构不匹配，或者用户明确要求另一种边界，就具体说明差在哪里。重要实验条件仍要指出，但只解释它会影响的步骤，不能让一个未知条件吞掉已经得到的材料结论。

也不会把回答改成无条件保证成功。某条染色体上的匹配不能等同于全基因组唯一，文件正确不能等同于最终生物学效果已验证。

## 4. 怎样判断 Trace 是否干扰设计

用同一模型、同一材料和相同用户信息，分别测试不采集、只记录事实、记录事实并组织解释三种模式。重复小样本，检查的是：主结论有没有改变、有没有新增无必要工作、是否还会发现真实错误、交付是否完整，以及实际多用了多少时间和工具调用。

设计过程中仍保存真实工具事实，重要选择的公开说明可以同期留下。稍后整理报告不允许假装恢复模型当时未公开的想法。

这次先不修改全局默认模式。只有结果支持时，才决定是否把日常默认改为 Observed，或继续缩减 Full 的设计阶段负担。没有 token 数据就写未知，不声称零成本。

## 5. 点开详情究竟看什么

**选择详情**：选了什么，理由是用户给的还是 AI 当时公开说的，哪些材料支持哪个方面，限制是什么，影响了哪些步骤或文件。没有原理由就明确缺失，不补故事。

**文件详情**：这是什么文件、用来做什么、属于候选还是正式交付、来自哪些材料和动作、哪些检查对应它。文件名可区分，入口能打开。

**证据详情**：来源名称、有关片段、这次设计如何使用它、哪些结论不能由它推出。来源真实存在不等于适合当前设计。

内部编号、Schema、哈希和原始 JSON 仍保存，用独立“技术记录”入口供排查。它们不再占据默认详情。展开后难懂，仍然算报告失败，不能以“信息已经给全了”通过验收。

## 6. untraced 与大文件怎样处理

untraced 表示当前文件没有找到对应生成记录，不表示文件不存在或内容错误。新版应说明具体文件和缺失环节，并放在“记录完整性”；实际缺文件或版本不对，才同时进入交付问题。

不能为了消除 untraced 补造历史。今后的脚本写文件应在发生时被记录；之前的未知文件可以保留，状态如实解释。

完整事实在数据层保留，报告引用需要的部分。现在的大文件至少存在多处重复展开，不能未经分析就认定全是 DNA 内容过长。开发目标是把本轮两个大 HTML 分别降至 5 MiB 内且小于原体积的十分之一，并验证离线阅读与实际打开时间。缩小文件不能靠删掉失败或证据。

## 7. 怎样判断本轮完成

先检查文件和任务，再检查记录和页面：

1. 原先出错的引物导出确实完成，保存文件的序列、引物、注释与预期一致。
2. 现成材料任务能明确得出“不需新设计”，真实冲突任务仍被正确识别；没有靠忽略检查换取好听的结论。
3. 每份本轮新交付文件能对应实际操作，方案和已生成的 Trace 在首次交付就有有效入口。
4. 不读技术记录，也能解释项目目标、一个关键选择的理由、依据范围及最终文件用途；所有“查看”都确实能查看。
5. 大报告能正常打开，历史、失败及未知仍然保留。普通任务没有的栏目不会被硬凑出来。

最初仍按已确认视觉方向做，不再花主要精力更换皮肤。你认可的方案网页与替换示意图会作为主任务表达的参考，Trace 用于补充追溯，不能挤走主方案。

## 8. 范围与遗留问题

本轮依次做：固定原案例 → 主任务/提示词与文件正确性 → 采集和体积 → 默认正文/详情 → 真实任务与回归。可以分步验证和提交，不做一次性庞大框架重构。

前序 pET 与本次 Chr1 注释问题会继续定位真实影响；不能靠删除注释、放宽标准或换题消掉阻塞。若仍无法正确解决，必须单列。全部闭源宿主活动的自动采集、宏观安全治理和湿实验成功不在本轮承诺内。

目前交付的是两版方案及更新后的规范，主 Skill 的复用优先和首次交付指引也已补充。业务代码、全局模式和 Codex/DSH 安装未变；完整提示词拆分、程序修复及实际效果在实施后逐项验收。
