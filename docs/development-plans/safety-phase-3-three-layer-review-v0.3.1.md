## 1. 我们要做成什么，哪些还没有决定

Evidence Trace 的用途是帮助研究者复核一次 AI 辅助设计：用户要求是什么；AI 提出了哪些选择；依据来自哪里；程序实际执行了什么；检查针对哪份文件；还有哪些事情缺少证据。

本项目的 Skill 是供 AI 调用的 DNA 检查、构建和文件输出工具。Evidence Trace 随这些工作保存记录，它不代替原来的 DNA 计算程序。

它的可信度应来自可回查的材料和明确的对应关系。AI 当时留下的说明很有用，但“AI 说自己因为某篇论文而选择某方案”，首先是一项公开声明，不能直接当作已证实的内部原因。

我们已经讨论形成的方向是三层：

- **采集层**负责取得和保存原始记录。
- **数据层**负责整理这些记录的关系，核对程序能够核对的部分。
- **报告层**负责组织成研究者能理解的报告，HTML 是主要形式。

这三个名称表示同一个软件中不同部分的职责，不需要研究者安装三套软件。用户不应被要求手写程序数据；正常情况下由设计 AI 和程序完成提交，研究者查看关键选择与原始依据。

本文提出的具体采集范围、来源保留方式、交付核对和报告输出，需要人工评审。写入方案不表示功能已经实现，也不表示所有细节已冻结。

## 2. 为什么现在需要重构

2026 年 9 月 15 日，我们让子代理真实查文献、使用完整 GFP 源质粒和表达载体，设计对照与 A206K 候选。候选用于进一步研究较低的 GFP 自聚倾向，并不意味着已经验证其实际性能。

GFP 是绿色荧光蛋白；A206K 表示把其第 206 位氨基酸从丙氨酸改为赖氨酸。这里的重要信息是“为什么选择这一处变化，以及实际文件是否只发生了预期变化”，不要求读者先理解全部分子生物学细节。

这次运行得到了几类不同结果：

- 两份新版候选的关键序列、实际 PCR 材料链和引物检查成立。PCR 是扩增 DNA 的步骤，这里核对的是它实际使用的模板和得到的中间材料。
- 软件的正式交付检查被载体注释问题拦住，因此不能称已经完成正式交付。
- 第一次酶切失败，以及因此修改路线的说明，进入了 Trace。
- 最后增加测序引物后产生的四份新 QC 文件，没有进入 Trace 的产物记录。QC 在这里指用于检查构建的验证设计。
- 论文和理由有记录，但一些来源只写“本地检查”，不能直接回到具体原消息或程序输出。

因此，问题并不是没有页面，也不是所有记录都无效。需要补齐的是：哪些动作会被记录；记录能否找到原始出处；后续文件是否仍然连接在同一次设计中。

| 层 | 本层要回答的问题 | 应交给下一层的信息 |
|---|---|---|
| 采集层 | 实际收到了什么、发生了什么？ | 原始内容、出处、时间和对应对象 |
| 数据层 | 哪些记录确实有关，哪些关系还只是声明？ | 已连接的过程、关系来源及缺口 |
| 报告层 | 研究者怎样看懂和复核这次设计？ | 清楚的过程报告、文件入口和详细记录 |

## 3. 一次设计怎样经过三层

先说明三个容易混淆的词。

**任务**是用户提出的一次设计委托。**运行**是程序执行的一次工作流，例如一次突变制备或一次克隆。**操作**是其中某个具体动作，例如读取材料、运行检查或写出文件。一个任务可以有多次运行和多项操作。

以这次 GFP 工作为例，重构后希望这样处理：

| 实际过程 | 采集层留下什么 | 数据层怎样连接 |
|---|---|---|
| 用户要求两组使用相同表达背景 | 原要求或明确标为摘要的转录 | 将其作为后续选择回应的要求 |
| AI 查阅候选变体资料 | 能取得的相关原文、来源位置及获取记录 | 将原文与提交的文献判断对应；不自动认定判断成立 |
| AI 选择 A206K 和制备路线 | 公开选择、简短理由及其引用 | 保存“AI 声称依据什么作出选择” |
| 程序执行首次酶切方案并失败 | 实际输入和错误结果 | 确认哪个方案对应这次失败 |
| AI 说明改用另一组酶 | 新选择与对原失败的引用 | 保存这次修改及公开理由，保留旧选择 |
| 程序制备并继续使用中间体 | 实际输入、中间文件和后续调用 | 确认后一步收到的是哪份实际中间体 |
| 为 QC 文件增加测序引物 | 修改前的文件身份、标注操作及新文件 | 把新版 QC 文件接回原文件和操作 |
| 准备交付文件 | 明确的文件清单及逐文件核对 | 分清能追溯、缺失记录和找不到的文件 |

报告层随后把这些已明确的信息排成可读过程。它不重新猜“为什么选择 A206K”，也不因为两个动作先后发生就写成因果关系。

## 4. 采集层具体收什么，谁来提供

### 4.1 程序可以自动取得的内容

程序执行工具时，本身就能知道：收到哪个文件、参数是什么、调用是否成功、返回了什么、写出了哪些文件。将这些内容保存下来，不需要另一个 AI 解读。

本轮建议先完整接入七种已有入口：结构化构建、组合流程、标准构建路线、质粒检查、引物标注、格式转换、导出文件包。后三类很容易发生在主要构建结束之后，但同样会改变最后交给用户的文件。

暂时没有接入的独立脚本必须如实列在范围外。程序不能仅凭某个文件出现在目录里，就知道它是怎样生成的。

### 4.2 需要 AI 或用户明确提供的内容

这些内容主要包括：研究目的、用户约束、真正有取舍的设计选择、公开理由、文献支持哪个判断、已知限制，以及实际考虑过但放弃的方案。

这部分不能完全自动获得。我们要让 AI 少重复填写程序已有的数据，把提交集中在需要理解的内容上。也不要求每次任务必须有替代方案、论文或用户否决情节。

例如“用户要求保留终止密码子”就归用户要求。终止密码子用于结束蛋白翻译；遵从这个要求不应被包装成 AI 自主作出的创新选择。

### 4.3 外部材料怎样保留

建议增加一个小型材料观察入口：程序从明确指定的文本文件中提取相关行，保存原文和位置；也可以接收提交者提供的文字，但必须区分两者。

| 情况 | 能说明什么 |
|---|---|
| 程序从给定文件提取原文 | 能复核这份文件中存在这些文字 |
| AI 转述一段论文内容 | 能知道 AI 提交了这个说法，需要再核对原文 |
| 有可靠宿主原消息 | 可以进一步核对公开发言、工具返回及先后关系 |
| 只有“刚才查过”这样的描述 | 无法定位原记录，来源仍然不足 |

“宿主”指运行设计 AI 的应用。只有需要自动读取 Skill 之外的公开消息和检索记录时，才需要考虑它提供什么接口。第一版不以建设通用宿主适配为前提。

即使程序读到了一个用户提供的对话导出文件，也只能先确认文件内容，不能自动证明文件没有被编辑。软件应准确说明核对到了哪一步。

### 4.4 采集范围和故障

同一任务使用同一个记录目录，让多次运行能够关联。没有提供这个关联信息的独立操作可能仍会漏出任务，交付核对可以发现部分缺口，但不能找出从未向系统提及的全部活动。

普通模式下，Trace 出错应保留 DNA 工作的实际结果，并提示记录不完整。只有明确选择严格模式时，才可以在调用边界停止。记录功能不应默认成为设计工具的单点故障。

## 5. 原始记录保存成什么，怎样保留历史

原始记录继续保存到 `events.jsonl`。JSON 是一种有名称和对应值的结构化文本；JSONL 表示每行保存一条独立记录。它便于程序读取，也能用文本工具查看。

每条记录会有编号、记录时间、所属任务和运行，以及具体内容。编号用于准确引用某条记录，不代表评分或可信等级。

关键规则有四条：

1. **原记录保留。** 改设计时追加新版本，旧方案和失败不会被覆盖。
2. **时间含义明确。** 写入日志的时间，不一定是用户说话或 AI 作出选择的时间。
3. **后来补充单列。** 后来找到的论文可以支持原选择，但不能改写成当时已经使用的依据。
4. **文件版本明确。** 同一路径的文件被修改后，属于新的文件状态；序列没变，也可能增加或删除了引物和注释。

记录保存材料的位置和内容标识，不等于软件自动备份了所有原始 DNA。如果用户覆盖或移走旧文件，报告应说明无法再取得旧内容，不能承诺一定可以重跑。

## 6. 数据层怎样处理关系，为什么不需要所有工作都交给 AI

程序能够连接明确的记录，但不能从没有关联的数据中理解完整研究逻辑。数据层因此要区分关系的来源。

| 关系 | 谁提供依据 | 程序可以核对什么 |
|---|---|---|
| 某文件被用作输入 | 实际调用记录 | 路径和内容版本是否对应 |
| 某操作生成某文件 | 实际操作和输出记录 | 输出是否存在，是否属于该次调用 |
| 新 QC 文件来自原 QC 文件 | 文件标注操作 | 修改前后文件及操作是否对应 |
| 某决定回应某要求 | AI／用户提交 | 引用的要求是否存在、版本是否明确 |
| 某段论文支持某项判断 | AI／人理解后提交 | 能否找到对应片段；支持关系本身还需科学复核 |
| 因为失败而改变方案 | 当时公开说明加失败记录 | 失败是否真实、说明引用是否正确；不能由先后顺序证明内部原因 |

“先发生”“作为输入”“支持判断”需要保留不同含义。报告里也不能用同一种没有说明的箭头，让读者误以为它们都是因果关系。

### 6.1 程序整理的实际顺序

先识别记录及版本，再连接明确引用；随后核对实际参数和文件，比较已填写的实验条件，最后整理变化和缺口。

例如，AI 声称使用模板 A，调用记录却显示收到模板 B，程序可以指出不一致。若 AI 说“论文证明这个候选适合当前条件”，程序仅凭宿主、温度等字段相同，仍不能确认科学结论成立。

数据层也不能把一次整份文件检查复制到所有判断下面，暗示每个判断都被验证。检查只适用于原程序实际检查过的对象和范围。

### 6.2 怎样发现交付文件漏记

交付前明确列出准备交给用户的文件。程序逐份检查：

- 文件能否找到；
- 它是否对应已经记录的版本；
- 能否回查生成或修改操作；
- 是否存在多个无法区分的来源。

本次漏掉的四份 QC 文件，在这样的核对中应该被标为“文件存在，但缺少生成记录”。系统可以补记此刻发现了文件，不能因此补造之前的标注过程。

核对清单全部通过，只表示这份明确清单中的文件可以追溯。它不代表 DNA 已通过正式交付，也不代表所有宿主行为都被捕获。

### 6.3 不同问题不要合成一个绿灯

报告要分别说明：日志是否可正常读取；采集覆盖哪些入口；清单文件能否追溯；AI 说明的来源是否可核对；实际设计检查有没有失败。

这能避免再次出现“记录完整”的字样，却让读者误以为任务已经完整记录、设计已经正确、最终文件已经通过检查。

## 7. 报告层应该长什么样

报告层接收数据层已经整理好的过程。它决定哪些内容先读、哪些展开、如何解释原状态，但不重新建立科学支持关系。

建议报告使用以下结构。栏目按真实内容出现，简单任务无需填满。

| 读者看到的内容 | 帮助回答什么 |
|---|---|
| 任务背景与本次目标 | 为什么做这次设计，准备得到什么 |
| 用户要求与关键选择 | 哪些已经由用户规定，AI 还有哪些取舍 |
| 理由、证据和限制 | 为什么这样选，依据支持到哪里 |
| 执行与修改过程 | 实际做了什么，哪里失败，怎样调整 |
| 检查与文件 | 检查适用于哪份文件，交付的是候选还是正式产物 |
| 具体未解决事项 | 现在还有什么需要处理，原始材料在哪里 |

例如，针对上次任务，报告应明确表达：

> 用户要求两组使用相同表达背景。AI 选择 A206K 候选。最初的酶切方案被程序拒绝，随后改变路线。两份候选的关键序列和引物通过核对，但正式交付仍被注释检查阻塞。最后新增的 QC 文件存在，而旧 Trace 缺少这一步的记录。

上面描述的是已审查的实际情况，不是重构已完成后的新记录。重构后的目标是让最后的文件标注也自动有记录，同时继续如实显示尚未解决的正式交付问题。

### 7.1 HTML 是主要形式

HTML 是可在浏览器打开的报告文件。它提供三种查看方式：

- **正文阅读**：从背景、过程读到结果。
- **思维导图**：查看整体过程、实际分支及其关系。
- **分栏阅读**：一侧选择过程步骤，另一侧看相应细节。

三种方式使用同一份报告内容，切换后仍保留选中的步骤。原文、版本和详细日志可以展开查看；重要失败与候选身份不能完全藏起来。

同一份内容还可导出 Markdown，即普通文本形式的报告。PDF 留到以后，不为第一版增加额外输出工程。不同形式不能各自重新判断证据关系。

### 7.2 报告为什么可以重新生成

`graph.json` 保存程序整理后的关系，`report.json` 保存报告的内容组织，HTML 和 Markdown 负责输出。这些都是由原始事件计算出来的文件，丢失后可以重建。

它们不是新的原始记录。修改页面布局不能改掉证据关系，重新生成报告也不能给过去增加一次不存在的检查。

## 8. 现有软件会改哪些地方

| 部分 | 保留 | 调整 |
|---|---|---|
| 原始记录 | 追加日志、旧版本和真实结果 | 增加来源观察与交付核对信息 |
| 工具采集 | 已有三条主要执行路径 | 补齐选定的检查、标注、转换和导出入口 |
| 数据处理 | 现有参数匹配、条件比较和变化判断 | 把关系计算集中起来，让报告不再重复计算 |
| 报告 | 已完成的可读过程结构和静态稿经验 | 用同一份报告内容替换旧 HTML，并提供文本输出 |
| DNA 设计核心 | 原规划、计算、检查和正式交付规则 | Trace 重构不改变这些生物学行为 |

无需增加一个专门写理由的 AI，无需让用户换一套设计平台，也不需要新增数据库服务。未来若确实需要自动取得某个宿主的公开记录，再按实际接口做有限接入。

## 9. 出错时怎么办，成本怎样控制

没有原文的转述继续可以保存，但标明未核对；没有理由的操作仍可记录执行过程；无法判断的关系保持未知。

旧日志保留，不要求用户重新整理全部历史。旧记录没有的来源和时间不能自动补成确定值。新读取程序会识别旧格式，但重新生成的报告应使用准确的新标签。

正常设计不增加独立解释模型调用。Full 模式让设计 AI 顺带留下重要选择的简短说明；Observed 模式保留实际记录和已有说明，不要求额外解释；Off 不新增 Trace。开发默认仍是 Full，发布默认还需比较实际效果和成本。

程序自动写日志也有本地处理成本，AI 提交材料也可能增加工具轮次。因此应测整项任务的时间、输入输出 token 和轮次，不仅计算理由写了多少字。

原始 DNA、凭据和无关对话不默认进入普通日志。不同程序同时写同一份日志时，要避免写坏记录；第一版仍按单个写入者工作，不能伪称已经支持多人并行协作。

## 10. 怎样开发，怎样判断做成了

按五个实际交付步骤推进，不先搭一个大框架。

| 顺序 | 做什么 | 人工能检查的结果 |
|---|---|---|
| 1 | 确认规则，先接通引物标注到交付核对 | 一份新 QC 文件能追到原文件和标注操作 |
| 2 | 补齐选定入口与来源记录 | 原文、调用和文件有具体出处，失败不漏掉 |
| 3 | 集中数据层关系处理 | 没有 HTML 也能查清来源和关系，未知处不被填成事实 |
| 4 | 完成统一报告与 HTML | 正文、导图、分栏与文本报告内容一致、容易理解 |
| 5 | 重跑真实任务并验收 | 最终文件、真实过程与报告逐项对应，主设计行为保持一致 |

本次 GFP 案例继续使用，但不让 AI 照抄旧故事。若新运行没有相同失败，就按实际过程记录；原失败输入另用于检查软件是否仍能发现原问题。

工程检查包括：开关 Trace 后相同输入的 DNA、注释、引物及检查含义一致；晚补内容不改历史；同名新文件不继承旧检查；程序失败和采集失败能区分。

人工检查应让未参与设计的读者回答：用户想得到什么；AI 真正选择了什么；一项选择依据什么；哪次检查对应哪份文件；哪里改过；哪些部分还没有证据。答不出来，就继续改报告组织。自动测试通过不能替代这项检查。

文献记录也必须实际验一次：至少一项关键依据保留原资料或原工具返回中的具体片段，不能所有来源都标为未知就宣布来源采集完成。

另有一个必须分开处理的问题：原载体和转换后 CDS 注释阻塞了正式交付。CDS 是文件中标记蛋白质编码区域的一类注释。Trace 可以准确记录这一失败，但只有主线问题也得到修复，才能声称该完整设计流程可发布。

## 11. 人工审查清单与仍待决定的事项

阅读完本文，建议逐项判断：

- [ ] 是否同意先覆盖这七类已有工具，而不承诺观察任意脚本和全部宿主活动？
- [ ] 是否同意原材料可取得时保留具体片段，只有转述时明确保留转述身份？
- [ ] 是否同意程序关系与 AI／人的科学判断关系分别记录，不能混成同一种证明？
- [ ] 是否同意交付前对明确文件清单做追溯核对，并把它与 DNA 正式交付检查分开？
- [ ] 是否同意报告的正文、导图和文本输出共用同一份内容，不在生成页面时补写研究故事？
- [ ] 是否同意扩展记录格式，但继续读取旧记录并保留原始历史？
- [ ] 是否能接受第一版仍无法自动观察所有宿主活动，但必须显示真实覆盖范围？
- [ ] 是否同意把 CDS 注释阻塞单独修复，不能为让报告好看而放宽检查？
