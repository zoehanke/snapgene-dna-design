# Evidence Trace 三层重构：人工理解与审查

**r2 · 2026-09-19 · 方案已根据讨论更新，业务代码尚未开发。**

本文面向不熟悉编程的项目负责人。[开发版](safety-phase-3-three-layer-design-v0.3.1.md)按相同章节给出接口和实施要求；[JSON 示例](safety-phase-3-process-example-v0.3.1.json)展示一份完整机器结果的形状。示例是模拟内容，不是新的实际实验结果。

## 1. 这次方案最重要的变化

本项目的 Skill 负责 DNA 检查、构建和文件输出。Evidence Trace 的用途是保留用户、AI 和程序共同形成设计的经过，使研究者能复核选择、依据、检查及产物。

上一版把数据层写得过于像“程序连接记录”。现在明确：**程序能核对事实对应，但完整设计逻辑需要 AI 或研究者理解和组织。**

另一个变化是报告：哪些内容先讲、如何摘要、图里怎样分组，确实需要作者判断。这部分保存为“报告编排方案”，可以由整理数据的 AI 一并完成；固定程序随后按方案生成 HTML。

我们不追求保存模型不可见的内部思维。目标是完整保存已取得的相关信息，形成可复核过程，并分清当时公开说明、后来整理和未知内容。

## 2. 三层分别由谁做什么

| 层 | 工作 | 谁完成 |
|---|---|---|
| 采集层 | 留下实际操作、输入输出、原始要求、公开说明和相关原材料 | 程序自动记录，加上 AI／用户提交 |
| 数据层 | 将信息组织为完整设计过程，核对引用、版本和实际结果 | AI／人做语义组织，程序做事实与结构核对 |
| 报告层 | 决定读者怎样阅读，再生成页面和文本 | AI／人提出编排，程序执行编排 |

同一个设计 AI 可以同时完成过程组织与报告编排，但这仍然是 AI 工作，会消耗输入输出和时间。不能因为没有额外模型服务，就说整个过程由程序自动理解完成。

## 3. 数据层最终要交出怎样的结果

最终结果应与给人看的报告表达同一段设计经过，但内容更完整、字段更明确。它不只是一堆带标签的节点。

| 部分 | 内容 |
|---|---|
| 任务上下文 | 为什么设计、用户要求、现有材料和预期交付 |
| 原始记录 | 用户原话或摘要、公开说明、程序返回、来源及版本 |
| 已组织过程 | 阶段、步骤、实际分支、选择、修改及其依据 |
| 完整细节 | 每项选择的公开理由、相关原文、条件、限制和检查范围 |
| 结果与缺口 | 得到哪些文件、哪些检查成立、哪些问题未解决、哪些记录未能归类 |
| 报告编排 | 面向人的标题、摘要、阅读顺序、导图分组及展开安排 |

例如“确定酶切路线”应该作为一个阶段，说明它要解决什么问题；下面再连接原方案、实际失败、调整说明和新方案。单独列出这些名词，却没有组织关系和具体说明，不算整理完成。

数据可以按图结构保存，支持分支和交叉引用。阶段提供主线，一份证据可以关联多个选择，同一个中间体也可以进入多个分支。图形坐标和节点数量不能限制完整数据的保存。

完整记录保存一份，用编号在多处引用；不为每张图复制一份不同版本的证据。无法归类的记录仍要保留为“未归类”，不能因为不适合展示而消失。

## 4. 采集层怎样取得这些内容

### 程序自动取得的部分

工具执行时直接知道输入、参数、返回、错误和写出的文件。本轮先补齐七类入口：结构化构建、组合流程、标准构建路线、质粒检查、引物标注、格式转换、文件包导出。

这次真实测试的四份新版 QC 文件没有进入 Trace，正是因为最后的引物标注没有接入。QC 是用于检查构建的验证设计，属于实际交付过程，不应在主要构建结束后失去记录。

### AI 或用户提供的部分

研究目的、约束、选择理由、论文支持哪个判断等，需要明确提交。用户已经规定的条件应保留为用户要求，不能包装成 AI 的自主选择。

资料能够取得时，程序保留具体原文和位置。只有 AI 转述时，也可以保存，但不能称作核实过的原文。读取一份提供的文本，只证明其中有这些文字，不自动认证作者、发表时间或科学含义。

宿主是运行设计 AI 的应用。只有要自动读取 Skill 外的公开消息和搜索记录时，才需要考虑它的接口。第一版不依赖建设通用宿主平台；无法取得的部分必须说明。

### 交付前核对文件

明确列出准备交给用户的文件，程序检查每份文件是否存在、版本是否对应、是否能追到生成或修改动作。文件存在但没有生产记录，就指出缺口，不能补造历史动作。

这项核对不代替 DNA 正式交付检查，也无法发现完全未向系统提及的文件。

## 5. AI 在什么时候整理，实际怎样参与

建议在主要设计阶段结束、重要修改后或交付前进行整理，不在每次工具调用后增加一次解释工作。

实际过程是：

1. 程序给出当前任务的记录目录、索引和截止位置。
2. 当前宿主 AI 读取任务、索引及相关原记录。
3. AI 写出已经组织好的设计过程，可以同时写报告编排。
4. 程序核对引用、版本及结构，保存该组织版本。
5. 程序把原记录与组织结果装配成完整 JSON。
6. 固定程序按已有编排生成 HTML 或 Markdown。

AI 不需要重新抄写所有程序返回。原始输入、检查、文件和数值由程序直接放进完整结果，AI 主要提交组织、解释和引用。

必须分清三种内容：

- **原始说明**：设计者当时公开说了什么。
- **整理摘要**：后来根据这些公开记录归纳出了什么。
- **后续解释**：后来新提出的判断或可能原因。

后两者可以有价值，但不能写成设计者当时已经想过。缺少原始理由，就保留缺失。

Full 模式在阶段结束或交付前要求宿主完成这项整理；Observed 默认只保留事实和已有提交，不额外要求整理。用户明确请求整理旧记录时，可以进行，但必须注明这是后来整理并计入成本。Off 不新增记录或组织版本，已有结果仍可阅读。

## 6. 程序负责哪些核对，哪些不能保证

| 能核对 | 不能仅靠这个核对保证 |
|---|---|
| 某个引用编号是否存在 | 被引用的内容真的支持那句话 |
| 文件版本是否与检查对象一致 | 所有科学目标已经被验证 |
| AI 提交的参数是否对应实际输入 | 这些参数是最合理的选择 |
| 所有相关记录是否有保存去向 | AI 的归类和摘要完全正确 |
| 报告图只使用已有步骤和关系 | 所有关系都反映真实科学因果 |

因此，程序通过只能表述为“结构和引用检查通过”。科学判断及文字忠实度仍需 AI／研究者复核，不能用一个成功标记包办。

我们还需要单独保存“记录截至哪里”。如果后来又增加了文件、检查或要求，旧的过程组织虽然仍可查看，但应明确标为针对旧记录。不能把旧摘要套在新结果上。

如果 AI 尚未完成整理，程序仍可显示有限的实际执行记录，并说明“设计过程尚未整理”。不能自动把这份事实列表称为完整设计逻辑。

只想聚焦某次运行时，也不能删掉摘要的一半依据却保留完整结论。页面需要保留相关背景；如果要求只看某个历史时刻，就使用对应范围的旧组织，没有合适组织时明确只显示事实。

## 7. 报告怎样省略、分组和画图

报告编排也是需要 AI 或人判断的工作，不应再隐含地说成程序自行完成。可以与数据整理同一次产出，但逻辑上分开保存。

| 编排内容 | 例子 |
|---|---|
| 报告标题 | 为什么更换酶切路线 |
| 章节顺序 | 先讲原方案问题，再讲新方案及其状态 |
| 短摘要 | 原方案因额外切点被拒，AI 提出改用另一组酶 |
| 图中短标签 | 原路线、发现问题、提出新路线 |
| 默认展开 | 新方案尚无执行记录这一重要限制 |
| 详情入口 | 原错误、完整公开说明、具体版本和依据 |

这些安排都通过编号引用完整过程。短标签不替代完整说明，详情收起不表示数据删除。

报告程序负责尺寸、间距、连线和交互。阅读顺序不能创造因果边；两个步骤没有已记录关系时，只能作为同组内容展示。

正文、思维导图和分栏阅读共用同一份过程和编排。改变主题、缩放、展开、导出，不需要 AI。换受众或重新选择重点时，才可能请 AI 修改编排，原始事实和完整过程不因此改变。

程序还要固定显示文件的实际角色和检查状态，防止摘要把候选说成正式交付，或省略会改变读者判断的未解决问题。已解决的历史失败可收起，但仍能回查；简单任务没有相关问题时不强制出现空栏目。

## 8. 文件形式和示例怎样读

JSON 是带明确字段名称和对应值的文本格式，程序可以直接读取。机器结果仍放在 graph.json，但现在它应包含完整过程和报告编排，不只是节点连线。

| 保存位置 | 保存内容 |
|---|---|
| events.jsonl | 逐条追加的原始记录，以及后来提交的组织和编排版本 |
| graph.json | 装配好的完整机器结果 |
| index.html | 主要的人类阅读页面 |
| report.md | 同一内容的 Markdown 文本报告 |
| TRACE-MANIFEST.json | 文件与记录范围索引 |

不再要求另存一份长期维护的 report.json。渲染过程可以有临时数据，但不再形成第二套科学组织结果。

附带 JSON 示例只演示一个小过程：原酶切方案失败，AI 公开提出新方案，新方案尚没有执行结果。其 design_process 已经把过程组织起来，report_plan 则决定怎样向读者简明表达。

示例中的全部引用都能找到对象，但这不意味着真实科研任务已验证。实际运行必须使用实际取得的记录，不能复制示例作为证据。

## 9. 软件需要怎样改

| 部分 | 主要改动 |
|---|---|
| 采集 | 接入遗漏工具，补原材料观察和文件清单核对 |
| 程序事实处理 | 集中输入输出、版本、原检查和已有关系计算 |
| AI 组织接收 | 新增读取事实快照、提交完整过程、校验保存组织版本的明确入口 |
| 报告编排 | 支持同次提交或单独修改，并绑定具体过程版本 |
| 报告生成 | 消费完整结果与编排，固定生成页面，不首次推断设计逻辑 |

设计 AI 将依据 Skill 指引执行“读取快照 → 组织 → 提交”的步骤。程序不会在没有说明的情况下调用另一模型。这个对宿主 AI 的依赖是方案的一部分，需要真实测试，不用更长的指导文字掩盖遗漏。

旧记录继续保留，缺少的来源和原时间不能倒填。旧页面和旧派生文件可以重新生成，但旧事实不改。未匹配新记录的旧组织需要明显标识。

DNA 计算、参数、检查标准和正式交付规则仍不由 Trace 修改。

## 10. 开发及人工验收

| 顺序 | 做什么 | 应看到的结果 |
|---|---|---|
| 1 | 确定完整 JSON、AI 提交包和报告方案契约 | 三种内容区别明确，示例引用可核对 |
| 2 | 补采集和文件追溯 | 最后增加引物的 QC 文件也有生成记录 |
| 3 | 接通 AI 整理与程序核对 | 得到已串联的阶段、分支、理由和结果，未归类信息仍保留 |
| 4 | 接通报告编排与输出 | 同一完整过程可生成简明报告，重复导出不再调用 AI |
| 5 | 重新跑真实任务 | 原操作、机器结果和用户报告逐项对应 |

人工需要分别检查机器结果与报告：

- 是否可以解释研究目标、真正的取舍、依据和实际结果？
- 是否保留了会影响判断的失败、未知和限制？
- 是否能从摘要回到完整说明及具体原始材料？
- 是否把后来整理的解释写成了当时原因？
- 是否把图上的阅读顺序写成了实际执行因果？
- 是否有记录因为不好展示而消失？

这次 GFP 案例继续使用，但不要求新 AI 重演旧故事。至少一项关键文献依据要保留实际原资料片段，不能所有来源都未知却声称来源功能完成。

同时测量 AI 整理和编排的次数、输入输出长度、工具轮次、耗时及实际完成情况。联合输出可能减少往返，但不会消除 AI 工作成本。

原任务的正式交付受 CDS 注释问题阻塞。CDS 是文件中标记蛋白质编码区域的一类注释。它需要单独修复；准确记录失败不等于完成了正确交付，更不能通过降低检查标准掩盖问题。

## 11. 当前保留的决定和未决项

已经明确保留：原始事件、真实程序结果、历史版本、正常模式不阻塞设计、未知不自动变成无关或安全。采集完整度、组织是否完成、科学判断是否成立分别表达。

尚需实际验证的是：怎样划分阶段最易读；大记录怎样分批让 AI 读取；联合生成与单独修改编排的成本；发布默认采用 Observed 还是 Full；是否需要某个宿主的原消息自动接入。

r2 已替换上一版“数据层主要靠纯程序整理”的设定。接口细节可继续审查，但后续实现不能退回只有零散记录和关系标签、没有完整设计过程的状态。

本轮只更新设计和规范衔接，没有开始业务开发。后续验收需要看真实输入、实际 AI 整理、程序检查和最终报告，不能只看测试数量。
